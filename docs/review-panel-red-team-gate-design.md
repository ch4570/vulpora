# 심사단 합의 게이트와 red team — 실행으로 판정하는 리뷰 설계

상태: **Proposed** (설계만, 구현 전)
작성일: 2026-11-23
기준 커밋: `698b670` (작업 브랜치 `docs/ch4570/verification-gate-designs`)
범위: 코드 리뷰 워크플로(`java-spring-review-workflow`, `kotlin-spring-review-workflow`,
`backend-code-review-workflow`, `architecture-review-workflow`, `security-scan-workflow`)의 판정 방식과,
변경을 실행으로 깨 보는 red team 경로. 이 문서는 스킬·에이전트·스크립트·CI를 바꾸지 않는다.
짝 문서: [접속 대상 관측과 모델 밖 차단](e2e-endpoint-isolation-gate-design.md)

> 앞선 논문 탐구 보고서(2026-11-23, 저장소 밖 문서)는 "LLM 심사단·다중 리뷰어 합의를 게이트로 쓰지 말라"고 했다.
> 이 문서는 그 판단을 뒤집지 않는다. 판단의 근거를 다시 읽고, 무엇이 달라지면 심사단과 red team이 게이트의 일부가
> 될 수 있는지를 설계한다.

---

## 1. 요약

- **"여러 모델이 동의했다"는 여전히 병합을 막는 근거가 아니다.** 다시 읽은 논문들은 보고서보다 더 분명하게 말한다.
  판정 모델 9개는 독립 표 약 2.18개 어치였고 패널 정확도(72.0%)가 가장 나은 단일 판정자(71.8%)와 차이가 없었다.
  다른 회사 모델끼리라고 해서 덜 비슷하게 틀리지도 않았다. 서로의 답을 보는 토론은 맞던 답을 틀린 답으로 바꿨다.
- **쓸 만해지는 길은 심사원 수가 아니라 정보원을 바꾸는 것이다.** 도구로 파일을 읽고 확인하는 판정자,
  실행으로 반례를 만드는 판정자, 생성 과정을 보지 않고 결과만 반증하는 검토자가 정확도·정밀도를 크게 올렸다.
  공통점은 "의견"이 아니라 "다시 확인할 수 있는 것"을 내놓는다는 점이다.
- **추천은 "실행 기반 공격자 + 소수 반증 심사원"을 핵심으로, 기존 리뷰 워크플로의 추정 결함을 공격자의 과제로
  넘기는 하이브리드(후보 C)다.** 새 투표 패널은 만들지 않는다.
- **판정 규칙은 단순하다.** 게이트 스크립트가 직접 다시 돌려서 재현된 결함만 거부권을 가진다. 재현되지 않은 의견은
  몇 명이 동의하든 신호다. 심사단은 승인하지 못한다("못 찾았다"는 안전하다는 뜻이 아니다).
- **사고 3(동시성 문제를 읽기만 하고 추정으로 끝냄)은 이 설계가 직접 겨냥한다.** 리뷰어가 `[inferred]`로 남긴
  동시성·트랜잭션 의심은 자동으로 재현 과제가 되고, 공격자가 run 소유 DB에서 병렬 재현 테스트를 만들어 돌린다.
- **설계 1(접속 대상 관측 게이트)이 먼저다.** 공격자가 실행하려면 그 실행이 공유 자원에 닿지 않는다는 보장이
  먼저 있어야 한다. 설계 1은 심사단 없이 기계적으로 되고, 심사단은 설계 1이 못 보는 "코드가 틀렸는가"를 더한다.
- **모델 규칙 안에서 된다.** 공격자·명세 테스트 작성자는 sonnet, 반증 심사원은 haiku 또는 sonnet으로 구성한다.
  opus는 필요 없다. 다른 회사 모델을 섞는 것은 근거가 약해 처음에는 하지 않는다.
- **단계**: 관찰만(그림자 실행) → 신호(리뷰 보고서에 표시) → 부분 게이트(보정 기준을 넘긴 위험 등급에서만 거부권).

## 2. 근거를 다시 확인한 결과

### 2-1. 확인 방법

- 보고서가 인용한 리뷰·판정 논문 11편과, 새로 찾은 다중 리뷰어·판사 합의·토론·red team·적대적 테스트 논문을
  하위 에이전트(sonnet) 3개가 나눠 열어 읽었다.
- 그 결과를 그대로 옮기지 않았다. **아래 표의 "직접 확인" 열이 "원문"인 수치는 제가 arXiv HTML 원문을 내려받아
  해당 숫자와 문장을 찾아 맞춰 본 것**이고, "초록"은 제가 초록 페이지를 직접 읽은 것, "2차"는 하위 에이전트가 원문을
  읽고 보고한 것을 옮긴 것이다.
- 대조하다가 하위 에이전트 보고의 오류 두 건을 찾아 고쳤다. AgentCoder의 "테스트 정확도 87.8 대 61.0"은 서로 다른
  표의 숫자를 짝지은 것이었고(실제 비교는 아래 표), Beyond Consensus의 "소수 거부권 최대 오차 2.8%"는 원문에서
  찾지 못했다(원문에서 찾은 값은 시험셋 4.4%).
- 웹 문서 안의 지시문은 데이터로만 다뤘다. 한 논문 페이지(CR-Bench)에 서식 지시문이 섞여 있었고 따르지 않았다.

정리하면 세 가지다.

1. **판정자를 늘려도 정보가 크게 늘지 않는다.** 실측 두 편 모두 판정자 10개 안팎이 독립 2~3.5개 어치였다.
2. **다른 회사 모델을 섞는 것은 기대만큼 독립성을 주지 않는다.** 계열 간 상관이 계열 내 상관과 거의 같았고(Nine Judges),
   프런티어 모델끼리는 회사가 달라도 더 비슷하게 틀렸다(Agreement Overstates). 작은 모델 실험이긴 하지만 섞은 팀이
   더 나빴다는 결과도 있다(Cost of Consensus).
3. **서로를 보게 하면 더 나빠진다.** 토론은 동조와 맞던 답 포기를 낳았고, LLM 중재자는 개입하지 않는 것보다 나빴다.

그리고 코드 리뷰 자체의 정밀도가 낮다(3.56~19.38% 범위). 이 위에서 다수결로 거부하면 틀린 거부가 쌓이고,
"올바른 코드를 틀렸다고 하는" 경향(73.2%)까지 겹치면 개발 흐름을 막는다.

공통점은 "의견을 늘린 것"이 아니라 **판정자가 다른 정보(실행 결과, 파일 내용, 반례)를 쓰게 하거나, 서로 다른 것을 보게
한 것**이다. 실행 결과는 모델이 몇 개든 같은 방식으로 틀리지 않는다. 이것이 이 설계의 출발점이다.

### 2-4. 여전히 근거가 없는 것

- 역할과 도구가 다른 검증자들이 **실제 코드 변경 리뷰에서** 얼마나 독립적인지 잰 논문은 이번에도 찾지 못했다.
  가장 가까운 후보("Three Agents Are Not Three Verifiers", NeurIPS 2026 목록)는 arXiv 본문을 찾지 못해 인용하지 않는다.
- LLM이 Java·Spring의 DB 수준 동시성 결함을 실행으로 재현한 성공률을 잰 논문은 찾지 못했다. CONCUR와 ConFixAgent
  ([2604.05753](https://arxiv.org/abs/2604.05753), 초록만 확인)는 Java 동시성이지만 교과서형 프로그램이다.
- 실제 리뷰 과정에 결함을 심어 미탐률을 잰 연구도 찾지 못했다. 그래서 보정(5-5절)은 우리가 직접 재야 한다.

## 3. 설계 질문에 대한 답

### (a) 심사원을 어떻게 독립시키나

독립성의 축을 효과가 확인된 순서로 쓴다.

1. **정보원: 실행 결과.** 가장 강하다. 실행으로 재현된 실패는 판정자가 누구든 같은 사실이다.
2. **입력 분리.** 같은 모델이라도 보는 것을 다르게 한다. 공격자는 변경과 코드를, 명세 테스트 작성자는 명세와 공개
   계약만(구현은 안 봄), 반증 심사원은 diff와 주장된 결함만 본다. OpenCodeReview의 반증 단계가 이 방식이다.
3. **역할(목표) 분리.** 깨는 쪽, 반증하는 쪽, 명세에서 기대값을 만드는 쪽의 목표가 서로 다르다. 같은 쪽이 구현과
   기대값을 같이 만들면 오류가 같이 간다는 점은 보고서의 원칙 2와 같다.
4. **서로 못 보게.** 모든 심사원은 같은 동결 스냅샷의 작은 증거 묶음만 받고, 다른 심사원의 출력이나 대화를 받지 않는다.
   토론 라운드는 두지 않는다.
5. **모델.** 가장 약한 축이다. 다른 회사 모델은 계열 간 상관이 낮지 않다는 근거 때문에 처음에는 쓰지 않는다.
   쓰더라도 반증 심사원 한 자리에만 실험으로 둔다(질문 3).

**작성자의 말은 숨긴다.** PR 설명, 커밋 메시지, 작성 에이전트의 "테스트했다", "하위 호환 때문에" 같은 설명은 공격자와
반증 심사원에게 주지 않는다. ImpossibleBench에서 감시자가 놓친 것이 바로 이런 그럴듯한 이유였다. 명세와 수용 기준은
작성자의 말이 아니라 승인된 요구사항에서 가져온다.

### (b) red team의 역할과 산출물

역할을 넷으로 나누되, 하나는 모델이 아니라 스크립트다.

| 역할 | 목표 | 보는 것 | 보지 않는 것 | 도구 | 모델 |
|---|---|---|---|---|---|
| **공격자(Breaker)** | 변경을 깨는 실패 테스트나 재현 스크립트를 만든다 | diff, 관련 코드, 승인된 명세·수용 기준, 리뷰어의 추정 결함 목록 | PR 설명, 작성 에이전트의 대화와 자기 평가 | 테스트 파일 작성(격리된 작업 트리), run 소유 환경 실행(설계 1의 감싸는 스크립트 경유) | sonnet(`standard/medium`) |
| **명세 테스트 작성자(Spec tester)** | 구현을 보지 않고 명세에서 수용 테스트를 만든다 | 명세·수용 기준, 공개 API 시그니처 | 구현 본문, 작성자의 테스트 | 테스트 작성, 실행 | sonnet. 위험 등급 높은 변경에만 |
| **반증 심사원(Refuter)** | 공격자가 낸 결함 주장을 반증한다: 재현이 계약을 잘못 읽었나, 불안정한가, 구현 세부에 기대고 있나 | diff, 결함 주장과 재현 코드, 계약 출처 | 공격자의 탐색 과정, 다른 반증 심사원 | 읽기, 재현 명령 실행(읽기 전용 결과 확인) | haiku(`frugal/low`)에서 시작, 보정 결과가 나쁘면 sonnet |
| **재실행 게이트(스크립트)** | 재현을 모델 대신 다시 돌린다 | 재현 명령, 변경 전·후 리비전 | — | 깨끗한 작업 트리 두 개에서 실행, 설계 1의 격리 영수증 확인 | 없음 |

게이트를 우회하려는 쪽(테스트 약화, skip 추가, 임계값 하향)을 잡는 역할은 따로 두지만, 모델이 아니라 보고서 후보 3의
**테스트 쪽 변경 감시 스크립트**로 한다. LLM 감시자는 SWE-bench 변형에서 42~65%밖에 못 잡았고, 우리 에이전트의 사고
과정을 감시자에게 줄 수 있는 구조도 아니다. LLM 감시는 신호로만 붙인다.

**인정하는 산출물은 실행으로 재현된 것뿐이다.** 결함 주장 하나는 다음을 모두 가져야 한다(가칭 `vulpora.red-team-finding/v1`).

- 주장: 무엇이 틀렸는가 한 문장, 위치(`path:line`)
- 계약 출처: 어떤 명세·수용 기준·공개 계약을 어기는가(구현에서 기대값을 만들면 안 됨)
- 재현: 테스트 파일 또는 스크립트, 정확한 실행 명령, 필요한 run 소유 자원
- 실행 기록: 변경 후 리비전에서 실패, 변경 전 리비전에서의 결과(새 동작이면 해당 없음과 이유), 시도 수와 실패 수
  (동시성은 R번 중 몇 번), 신선한 테스트 리포트 경로와 해시
- 격리 영수증: 설계 1의 `isolation-receipt.json` 참조. 없으면 이 주장은 실행 증거로 치지 않는다
- 반증 결과: 반증 심사원의 판단과 근거

공격자는 운영 코드를 고치지 않는다. 공격자가 만든 테스트는 격리된 작업 트리에만 있고, 저장소 테스트로 들어가려면
사람이 승인한다(질문 4). LLM이 만든 회귀 테스트가 결함을 정답으로 굳힐 수 있다는 보고서의 근거(원칙 2) 때문이다.

### (c) 언제 게이트이고 언제 신호인가

| 상황 | 효과 |
|---|---|
| 재실행 게이트가 변경 후 리비전에서 실패를 재현했고, 계약 출처가 있고, 반증 심사원이 근거를 들어 반증하지 못함 | **거부권.** 리뷰 판정을 `CHANGES_REQUIRED` 이상으로 올린다. 위험 등급이 높으면 `BLOCK` |
| 재현은 됐지만 반증 심사원이 근거를 들어 반증함(계약 오독, 구현 세부 의존 등) | 신호. 사람이 판단할 목록 맨 위에 둔다 |
| 동시성 재현이 R번 중 일부만 실패 | 변경 전 리비전에서는 0번이고 변경 후에만 실패하면 거부권. 양쪽 다 실패하면 기존 결함으로 신호 + 이슈 |
| 여러 심사원이 같은 결함을 말했지만 재현 없음 | 신호. 우선순위만 올린다. 높은 위험 등급이면 재현 과제를 만든다 |
| 한 심사원만 말한 결함(소수 의견) | 버리지 않는다. 높은 위험 등급이면 재현 과제로 넘긴다. 다른 LLM에게 중재를 맡기지 않는다 |
| 아무도 결함을 못 찾음 | 아무 효과 없음. 승인 근거가 아니다 |

이 규칙은 기존 리뷰 에이전트의 원칙("사실 전제가 확인되지 않은 CRITICAL/HIGH는 없다", "BLOCK은 `[confirmed]`
CRITICAL만")과 같은 방향이다. 달라지는 점은 `[confirmed]`의 뜻이 "읽어서 확신"이 아니라 "게이트 스크립트가 재실행으로
확인"으로 좁아진다는 것이다.

### (d) 군집 행동·아첨·상관 오류를 줄이는 방법

- **토론 없음, 병렬·블라인드.** 심사원끼리 출력을 보지 않는다. 동조 85.5%, 맞던 답 포기 같은 결과는 서로를 볼 때 생겼다.
- **중재는 실행이 한다.** 의견이 갈리면 다른 LLM에게 정하게 하지 않고 재현 과제로 만든다(LLM 중재자 순이익 −1.37%).
- **작성자 설명 숨김.** (a) 참고.
- **같은 계열의 자기 판정 금지.** 변경을 쓴 런타임·모델이 반증 심사원 자리를 혼자 맡지 않는다. 같은 모델 계열밖에 쓸 수
  없다면(지금의 sonnet·haiku 제약) 입력과 역할을 바꾸는 것으로 대신하고, 그 한계를 보고서에 적는다.
- **비교 판정은 순서를 섞는다.** 두 안을 비교하는 일이 있으면 순서를 바꿔 두 번 묻는다(순서만으로 14% 차이).
- **집계는 코드가 한다.** 결함 묶기와 판정은 위 (c) 표를 구현한 스크립트가 하고, LLM 종합기는 사람이 읽을 요약만 쓴다.
- **공통 오류를 잰다.** 보정 세트(e)에서 심사원 쌍마다 "둘 다 놓친 결함"의 비율을 기록한다. 공통 미탐이 높은 두 자리는
  하나로 줄인다. 같은 것을 놓치는 두 번째 심사원은 비용만 든다.

### (e) 심사단 자체를 보정하는 방법

보고서 후보 6(심은 결함으로 미탐률 측정)을 그대로 이 설계의 보정 장치로 쓴다.

1. **보정 세트.** 대상 스택(Spring·Kotlin·Java)의 작은 예제 서비스에 결함을 심은 변경 묶음을 만든다.
   - 동시성·트랜잭션: 읽고-고치고-쓰기에서 잠금이나 버전 제거, `@Transactional` 경계 이동, 격리 수준 변경,
     확인 후 실행(check-then-act) 순서 뒤집기, 멱등 키 확인 제거
   - 일반 논리: 경계값 하나 차이, 조건 반전, 필수 쓰기 제거, 권한 확인 제거
   - 테스트 쪽 약화: 단언 제거, skip 추가(테스트 쪽 변경 감시 스크립트의 시험용)
   - **결함 없는 변경**(대조군): 같은 크기의 정상 리팩터링. 틀린 거부를 재는 데 쓴다
2. **잴 것.** 역할별 재현율(심은 결함 중 재현까지 간 비율), 대조군에서의 틀린 거부율, 반증 심사원이 진짜 결함을
   반증해 버린 비율, 재현의 안정성(같은 결함을 R번 돌려 몇 번 재현), 심사원 쌍의 공통 미탐.
3. **강등 규칙(제안 값, 시험으로 조정).**
   - 거부권 유지 조건: 대조군 틀린 거부율 5% 이하, 거부권을 행사한 주장 중 사람 검토에서 유효한 비율 90% 이상
   - 하나라도 못 미치면 그 위험 등급에서 거부권을 끄고 신호로 강등한다. 다시 올리려면 다음 보정에서 기준을 넘어야 한다
   - 재현율은 거부권 조건이 아니라 "못 찾았다"를 얼마나 믿을지의 지표다. 재현율이 낮으면 보고서에 그 수치를 같이 적는다
4. **다시 재는 때.** 모델·프롬프트·스킬 버전이 바뀔 때, 분기마다. STANDARD §7의 "변경 후보는 안전·비용 회귀가 없음을
   증명한 뒤 승격"과 같은 규칙이다.
5. **과적합 방지.** 보정 세트의 일부는 숨겨 두고(심사원 프롬프트·예시에 쓰지 않음), 결함 유형을 돌아가며 바꾼다.
   실제 사고에서 나온 결함은 사람 검토 뒤에 세트에 추가한다.

### (f) 비용과 켜는 조건, 모델 규칙

**켜는 조건.** red team은 모든 변경에 돌리지 않는다.

| 조건 | 공격자 | 명세 테스트 작성자 | 반증 심사원 |
|---|---|---|---|
| 리뷰어가 `[inferred]` HIGH/CRITICAL을 남김 | 켬(그 의심만 과제로) | 끔 | 켬 |
| 동시성·트랜잭션·잠금·멱등성·권한·삭제·금액 관련 코드가 diff에 있음 | 켬 | 승인된 수용 기준이 있으면 켬 | 켬 |
| 리뷰어가 동시성을 MEDIUM("의도 확인 필요")으로 남김 | 켬(사고 3 유형) | 끔 | 켬 |
| 그 밖의 일반 변경 | 끔 | 끔 | 끔 |
| 사람이 명시적으로 요청 | 켬 | 선택 | 켬 |

**호출 수와 비용(추정, 측정 전).** 실제 값은 0단계 관찰에서 잰다.

| 구성 | 변경 하나당 에이전트 실행 | 토큰(대략) | 시간 | 비고 |
|---|---|---|---|---|
| 후보 A 정적 합의 심사단 | 심사원 5~9 | 심사원당 수만~수십만 | 수 분 | 리뷰가 에이전트형이면 건당 수백만 토큰도 나온다(OpenCodeReview Table 3에서 Claude Code 리뷰 건당 5,664K) |
| 후보 B 공격자 + 반증 | 공격자 1, 반증 1~2, 명세 테스트 0~1 | 공격자 수십만, 반증 수만 | 10~30분(대부분 테스트 실행) | 실행 비용이 토큰보다 큼 |
| 후보 C 하이브리드(추천) | B와 같음. 기존 리뷰 워크플로는 이미 돌고 있어 추가 비용 없음 | B와 같음 | B와 같음 | 과제 수에 상한(예: 변경당 재현 과제 3개) |

**상한.** 변경당 재현 과제 수, 공격자 1회 실행의 시간(예: 20분), 동시성 반복 횟수 R(예: 50)과 스레드 수, 토큰 상한을
둔다. 상한에 닿으면 남은 과제는 `NOT_RUN`으로 보고하고 신호로만 남긴다. 상한 도달은 더 비싼 모델을 쓸 이유가 아니다
(`docs/review-workflow-model-routing.md`의 기존 규칙).

**모델 규칙.** 오너의 현재 규칙(하위 에이전트는 sonnet·haiku, opus 금지) 안에서 전부 구성된다.

| 자리 | 저장소 프로필 | 오너 규칙 안의 모델 | 이유 |
|---|---|---|---|
| 공격자 | `standard/medium` | sonnet | 테스트를 쓰고 실행 결과를 해석해야 함 |
| 명세 테스트 작성자 | `standard/medium` | sonnet | 같음 |
| 반증 심사원 | `frugal/low`부터 | haiku, 보정이 나쁘면 sonnet | 입력이 작고 질문이 좁음 |
| 재실행 게이트, 집계 | 모델 없음 | — | 결정적 스크립트 |

**필요할 수 있는 예외(오너 결정).**
- 다른 회사 모델을 반증 심사원 한 자리에 쓰는 것. vulpora는 Codex 런타임도 지원하므로 기술적으로 가능하지만,
  코드가 다른 회사로 나가고 근거상 이득도 불확실하다. 처음에는 쓰지 않는다(질문 3).
- 저장소의 라우팅 문서는 보안·권한·되돌릴 수 없는 데이터 위험에 `frontier` 바닥을 둔다. 오너 규칙(opus 금지)과 부딪히므로,
  지금은 그 자리를 `ROUTE_UNAVAILABLE`로 두고 사람 검토로 넘기는 것을 제안한다(질문 7).

### (g) 사람이 개입하는 지점

- 명세와 수용 기준 승인(명세 테스트 작성자의 입력). 승인된 기준이 없으면 그 역할은 켜지 않는다.
- 공격자 테스트를 저장소 테스트로 편입할지 결정.
- 작성자가 거부권에 이의를 제기할 때의 최종 판단과, 거부권을 넘어가는 위험 수용(소유자와 만료일).
- 반증된 재현(재현은 됐지만 반증 심사원이 반대)의 판단.
- 보정 세트 관리와 강등·복귀 결정 확인.
- 다른 회사 모델 사용 여부.

## 5. 추천안: 후보 C

### 5-1. 흐름

```text
[리뷰]      기존 리뷰 워크플로(변경 없음): 결함 목록, [confirmed]/[inferred], 이견 보존
              │
[과제 선정]  스크립트: (c)·(f) 표의 조건으로 재현 과제 목록 생성, 상한 적용
              │
[재현]      공격자(sonnet): 과제마다 실패 테스트·재현 스크립트 작성 → 설계 1의 감싸는 스크립트로 run 소유 환경에서 실행
              │            (명세 테스트 작성자는 승인된 수용 기준이 있을 때만 병렬로)
[반증]      반증 심사원(haiku→sonnet): diff + 주장 + 재현 코드만 보고 반증 시도
              │
[재실행]    스크립트: 깨끗한 작업 트리에서 변경 후·변경 전 리비전으로 재현 명령을 다시 실행, 동시성은 R회
              │            격리 영수증 확인(없으면 실행 증거 아님)
[판정]      스크립트: (c) 표 적용 → 리뷰 워크플로 판정에 반영(거부권 또는 신호)
              │
[보고]      리뷰 보고서에 "재현된 결함 / 반증된 재현 / 재현 못 함(NOT_RUN 포함) / 신호" 네 묶음으로 표시
```

### 5-2. 사고 3을 이 흐름으로 다시 돌려 보면

1. `java-spring-review-workflow`의 `java-reviewer`가 "재고 차감이 읽고-고치고-쓰기라 동시 요청에서 갱신 손실 가능"을
   `[inferred]` MEDIUM(의도 확인 필요)으로 남긴다. 지금은 여기서 끝난다.
2. 과제 선정 스크립트가 "동시성 MEDIUM"을 재현 과제로 만든다.
3. 공격자가 run 소유 Postgres(Testcontainers)에 합성 데이터를 넣고, 같은 대상에 스레드 N개가 동시에 차감 요청을 보내는
   테스트를 쓴다(시작 시점을 맞추는 래치 사용). 계약 출처는 수용 기준의 "재고는 음수가 되지 않고, 성공한 요청 수만큼만
   줄어든다".
4. 재실행 게이트가 변경 후 리비전에서 50회 중 몇 회 실패하는지, 변경 전 리비전에서는 어떤지 직접 센다.
5. 반증 심사원이 "테스트가 트랜잭션 경계를 우회하지 않는가, 기대값이 수용 기준에서 왔는가"를 본다.
6. 변경 후에만 실패가 재현되고 반증이 없으면 거부권. 리뷰 판정은 `CHANGES_REQUIRED` 이상이 된다. 재현이 안 되면
   "R회 중 0회, 스레드 N개 조건"을 그대로 적고 신호로 남긴다. "추정"이라는 말 대신 무엇을 몇 번 해 봤는지가 남는다.

JVM 수준의 정밀한 인터리빙 탐색 도구(Java PathFinder, jcstress, Kotlin의 Lincheck 등)는 DB가 낀 Spring 서비스에는
바로 쓰기 어렵다. 처음에는 "고정된 작은 스레드 수 + 반복 + 변경 전·후 비교"로 시작하고, 순수 자료구조나 동시성 유틸리티
변경에서만 그런 도구를 검토한다.

### 5-3. 기존 자산을 쓰는 방법

STANDARD §7은 새 에이전트를 만들기 전에 결정적 코드나 기존 도구로 안 되는 이유를 적으라고 한다. 그래서 새 에이전트는
최소로 한다.

| 자리 | 후보 자산 | 이유 |
|---|---|---|
| 공격자 | `backend-test-author`를 "실패 테스트를 만드는" 과제 브리프로 호출 | 이미 테스트 작성·실행 권한과 격리 규칙(공유 인프라 금지)이 있다. 목표만 반대 방향 |
| 명세 테스트 작성자 | `qa-test-designer`(설계) → `backend-test-author`(구현을 보지 않는 브리프) | 보고서 후보 5의 경로 그대로 |
| 반증 심사원 | 새 좁은 스킬(가칭 `repro-refuter`) | 입력과 질문이 좁아 기존 리뷰어의 넓은 규칙 묶음이 오히려 맥락 과부하가 된다 |
| 과제 선정·재실행·판정 | 새 스킬(가칭 `red-team-probe`)의 스크립트 | 결정적이어야 하는 부분이라 모델에 맡기지 않는다 |

## 7. 설계 1과의 관계

- **설계 1이 먼저인 이유.** 공격자와 재실행 게이트는 실제로 앱과 테스트를 돌린다. 그 실행이 공유 Redis·S3·DB에
  닿지 않는다는 보장이 없으면, red team은 사고 1·2를 새로 만드는 장치가 된다. 보고서 질문 6("리뷰어가 run 소유 환경에서
  재현 테스트를 실행해도 되나")의 답도 "설계 1의 격리 증명이 먼저"였다. 그래서 red team의 실행 증거는 설계 1의 격리
  영수증이 없으면 증거로 치지 않는다.
- **설계 1은 심사단 없이 된다.** 접속 대상 대조, 샌드박스 차단, 소켓 관측은 모두 결정적이다. 모델의 판단이 필요 없고,
  보정할 필요도 거의 없다(거짓 양성은 예외 파일로 다룸).
- **심사단과 red team이 더하는 것.** 설계 1은 "어디에 붙었는가"를 본다. "코드가 맞는가"는 보지 못한다. 동시성 결함,
  트랜잭션 경계, 계약 위반은 설계 1을 완벽하게 통과한 실행에서도 남는다. red team은 그것을 실행으로 드러내고,
  심사단(기존 리뷰)은 어디를 공격할지 후보를 준다.
- **공유 장치.** 두 설계는 같은 감싸는 스크립트, 같은 영수증, 같은 Testcontainers 수명 관리를 쓴다. 따로 만들지 않는다.

## 9. 시험 방법 (구현 단계 시험 계획)

모든 실행은 설계 1의 격리 아래, 시험용 예제 서비스와 run 소유 컨테이너에서만 한다. 오너의 공유 자원은 쓰지 않는다.

| # | 시험 | 기대 결과 |
|---|---|---|
| R1 | 사고 3 재연: 갱신 손실이 있는 재고 차감 변경 | 공격자 재현 → 재실행 게이트가 변경 후에서만 실패 확인 → 거부권 |
| R2 | 같은 서비스의 올바른 구현(낙관적 잠금 포함) | 재현 실패 R회 중 0, 틀린 거부 없음 |
| R3 | 공격자가 구현 세부(내부 호출 순서)에 기대는 실패 테스트를 냄 | 반증 심사원이 반증, 신호로 강등 |
| R4 | 공격자가 기대값을 구현에서 가져옴(계약 출처 없음) | 검증 스크립트가 거부, 실행 증거로 치지 않음 |
| R5 | 격리 영수증 없는 재현 | 실행 증거로 치지 않음 |
| R6 | 작성자 설명에 "하위 호환 때문에 의도적"이라는 거짓 이유 포함 | 공격자·반증 심사원에게 전달되지 않음을 확인, 결과가 설명 유무로 바뀌지 않음 |
| R7 | 다섯 심사원이 같은 결함을 말했지만 재현 안 됨 | 거부 없음, 신호 |
| R8 | 한 심사원만 말한 동시성 결함이 실제로 있음 | 재현 과제가 만들어지고 재현됨 |
| R9 | 결함 없는 리팩터링 20건 | 틀린 거부율 측정. 기준(5%)을 넘으면 강등 규칙이 작동하는지 |
| R10 | 테스트 쪽 약화(단언 제거, skip) | 테스트 쪽 변경 감시 스크립트가 잡음. LLM 감시는 신호로만 기록 |
| R11 | 상한 도달(과제 5개, 상한 3개) | 2개가 `NOT_RUN`으로 보고되고 신호로만 남음 |
| R12 | 보정 세트 전체 | 역할별 재현율, 틀린 거부율, 공통 미탐 표를 산출 |

## 11. 확인하지 못한 것

- **코드 리뷰에서 역할·도구가 다른 검증자의 독립성.** 이번에도 직접 잰 논문을 찾지 못했다. 이 설계가 "입력·역할·실행
  분리가 모델 다양성보다 낫다"고 보는 것은 Agent-as-a-Judge, OpenCodeReview, Beyond the Verdict, AgentCoder의 결과를
  합친 해석이다. 각 논문은 그 자체로는 이 결론을 증명하지 않는다.
- **이 설계의 효과.** 위 논문들은 대부분 Python·경쟁 프로그래밍·자연어 과제다. Spring·Kotlin 백엔드에서 공격자가 얼마나
  재현하는지, 틀린 거부가 얼마나 나는지는 0단계에서 재야 한다.
- **비용 수치.** 3-(f)의 토큰·시간은 추정이다. 측정값은 OpenCodeReview의 건당 토큰(385K, 5,664K) 하나뿐이고 그것도 다른
  도구의 값이다.
- **2026년 논문의 심사 여부.** 인용한 2026년 논문 대부분이 동료 심사를 거쳤는지 확인하지 못했다. 단독 저자 논문(Nine

- **하위 에이전트가 읽은 것.** 하위 에이전트는 요약형 가져오기 도구로 읽었다. 그래서 "2차"로 표시한 수치는 원문 표와 다시
  대조해야 한다. 제가 대조한 것 중 두 건이 틀려 있었다(2-1).
