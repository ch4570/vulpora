# KB: 테스트 전략과 테스트 피라미드

"무엇을 **어느 레벨**에서 검증할 것인가"를 정하는 전략. 같은 결함을 가장 싸게 잡을 수 있는
레벨에서 잡고, 비싼 레벨(E2E)을 최소화하는 것이 핵심이다.

## 테스트 피라미드 (Fowler)
- **다수의 단위 테스트 → 적은 통합 → 소수의 E2E**. 위로 갈수록 느리고·비싸고·불안정(flaky)하다.
- 같은 비즈니스 규칙의 모든 분기를 위층(E2E)에서 반복 검증하지 말 것. 분기·경계는 아래층(단위)에서, 흐름은 위층에서.

```
        /\        E2E (소수)        — 핵심 사용자 흐름만
       /  \
      /----\      통합 (중간)        — 모듈 경계·외부 연동 계약
     /------\
    /--------\    단위 (다수)        — 로직·분기·경계·기법(EP/BVA/결정표…)
```

## 각 레벨이 책임지는 것
| 레벨 | 검증 대상 | 속도/비용 | 이 레벨에 둘 것 |
|---|---|---|---|
| **단위(Unit)** | 단일 함수/클래스 로직, 분기, 경계 | 빠름/저렴 | EP·BVA·결정표·상태전이 대부분, 알고리즘, 도메인 규칙 |
| **통합(Integration)** | 모듈 간 경계, DB 매핑, 외부 API 계약, 메시지 소비/발행 | 중간 | 리포지토리/영속성, 컨트롤러 슬라이스, 메시지 리스너 계약 |
| **E2E** | 배포된 시스템을 사용자 관점으로 통과 | 느림/비쌈/불안정 | 핵심 흐름(예: `Member` 가입→`Order` 생성→조회) 1~소수 |

## 트로피 변형 (정직 라벨)
- 일부 팀(특히 프론트엔드/서비스)은 **통합 테스트를 두껍게** 둔 "테스트 트로피" 형태를 선호한다.
  피라미드냐 트로피냐는 시스템 특성에 따른 선택이며, **핵심 원칙(싼 레벨에서 잡기·E2E 최소화)은 동일**하다.
  이 문단은 일반 업계 관례 요약이며 위 `source`의 직접 인용이 아니다(정직 라벨).

## 무엇을 어느 레벨에 — 의사결정 규칙
1. 입력 조합/경계/분기 → **단위**(빠르게 많이).
2. "이 모듈이 저 모듈/DB/큐와 올바르게 말하는가" → **통합**.
3. "사용자가 이 흐름을 끝까지 완료하는가" → **E2E**(핵심만).
4. 같은 검증이 두 레벨에 중복되면, **아래 레벨로 내린다**(비용↓, 안정성↑).

## 안티패턴 (아이스크림 콘)
- E2E가 비대하고 단위가 빈약한 **역피라미드**는 느리고 불안정하다. 이 신호가 보이면 분기 검증을 단위로 이동.

## 리뷰 훅
- [ ] 분기·경계·기법 기반 케이스가 **단위 레벨**에 배치되었는가(E2E로 끌어올리지 않았는가).
- [ ] E2E 시나리오가 **핵심 사용자 흐름 소수**로 제한되었는가(모든 규칙을 E2E로 검증하려 하지 않는가).
- [ ] 같은 동작이 여러 레벨에서 **중복 검증**되고 있지 않은가(가장 싼 레벨로 내렸는가).
- [ ] 통합 레벨이 모듈 경계·외부 계약(DB/큐/API)을 덮는가.
- [ ] 전체 비율이 역피라미드(E2E 과다)로 기울지 않았는가.
