# KB: 위험 기반 테스트 · 커버리지

전수 테스트는 불가능하다. 한정된 비용을 **어디에 깊이 쓸지**를 위험으로 정렬하고, **무엇을 얼마나
덮었는지**를 커버리지로 측정한다.

## 1. 제품 위험 (Product Risk) 산정
- **위험 수준 = 영향(impact) × 발생가능성(likelihood)** (ISTQB 리스크 기반 테스팅).
  - 영향: 결함이 났을 때의 피해(데이터 손실·결제 오류·핵심 흐름 중단 > 화면 정렬 어긋남).
  - 발생가능성: 결함이 실제로 있을 확률(복잡도·신규/변경 영역·과거 결함 이력·외부 의존).
- 위험이 높을수록 **더 깊게**(더 많은 기법·경계·네거티브), 낮을수록 **얕게** 덮는다.

### 우선순위 라벨 (산출물 규약 — 정직 라벨)
케이스 명세의 `우선순위` 컬럼에 사용. 아래 매핑은 본 저장소의 내부 규약이며 ISTQB 표준 등급이 아니다.
| 라벨 | 의미 | 기준(예) |
|---|---|---|
| **P0** | 반드시 통과(릴리스 게이트) | 핵심 흐름·결제·데이터 정합·보안 |
| **P1** | 높은 위험, 머지 전 권고 | 주요 비즈니스 규칙·경계·주요 네거티브 |
| **P2** | 보조/회귀 | 부가 기능·드문 조합·UI 디테일 |

## 2. 커버리지 종류 (무엇을 덮었나)
| 커버리지 | 측정 대상 | 비고 |
|---|---|---|
| **요구 커버리지** | 요구·인수기준 중 케이스로 덮인 비율 | 추적성 매트릭스로 측정(아래) |
| **위험 커버리지** | 식별된 위험 항목 중 케이스로 완화된 비율 | 고위험 미커버 = 즉시 보강 |
| **코드 커버리지** | 라인/분기/조건 실행 비율 | 실행 도구의 산출물(설계 단계가 아니라 실행 결과) — 높은 수치가 좋은 케이스를 보장하지 않음 |

> 주의: **코드 커버리지 100%가 결함 없음을 뜻하지 않는다.** 실행됐다는 것과 올바른 기대결과로 검증됐다는 것은 다르다.
> 설계 단계의 1차 지표는 **요구·위험 커버리지**다.

## 3. 우선순위화 절차
1. 변경/요구를 기능 단위로 쪼개고, 각각 영향·발생가능성을 평가해 위험 등급 부여.
2. 고위험부터 기법(EP/BVA/결정표/상태전이/페어와이즈)을 깊게 적용해 케이스 도출.
3. 각 케이스에 P0/P1/P2 부여 → 실행자가 게이트(P0) 먼저 돌릴 수 있게.
4. **추적성 매트릭스**로 요구↔케이스를 연결, 미커버 요구·고위험 공백을 드러낸다(상세 포맷: `test-case-spec-format.md`).

## 리뷰 훅
- [ ] 각 영역에 **영향×발생가능성** 기반 위험 등급이 부여되었는가.
- [ ] 고위험 영역이 더 깊게(더 많은 기법·경계·네거티브) 커버되었는가.
- [ ] 모든 케이스에 **우선순위(P0/P1/P2)** 가 명시되었는가.
- [ ] **요구 커버리지** 공백(케이스 없는 요구)과 **고위험 미커버**가 추적성 매트릭스로 드러나는가.
- [ ] 코드 커버리지 수치만으로 "충분"이라 단정하지 않았는가(기대결과 검증 여부를 함께 봤는가).
