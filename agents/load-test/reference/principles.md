# 부하 테스트 핵심 원칙 (Principles)

> 판단 기준 모음. 사실·규칙은 KB가 담고, 충돌 시 **KB(공식 문서)가 우선**한다.
>
> 출처: Grafana k6 문서(grafana.com/docs/k6), Gatling 문서(docs.gatling.io), Brendan Gregg "The USE Method"
> (brendangregg.com/usemethod.html), Spring Boot Actuator 문서(docs.spring.io/spring-boot).

## 0. 대전제: 허가된 대상, 합의한 부하
- 부하 테스트와 서비스 거부 공격의 차이는 허가와 통제다. 대상 소유 확인 → 계획 고정 → 중단 기준 → 실행 순서를 바꾸지 않는다.

## 1. 질문을 먼저 정한다
- "동시 사용자 N명을 버티는가"(closed 모델)와 "초당 N건이 들어올 때 어떤가"(open 모델)는 다른 질문이다.
  운영 트래픽처럼 사용자가 응답과 무관하게 도착하는 시스템은 open 모델이 더 정직하다. closed 모델은 응답이 느려지면 부하도 줄어 문제를 가린다.
- 목적에 따라 형태가 다르다: 기준선(정상 부하 유지), 한계 탐색(단계적 증가), 스파이크, 장시간 유지(누수·성능 저하).

## 2. 수치의 의미를 지킨다
- 평균은 꼬리를 숨긴다. p95/p99, 최대, 오류율을 함께 본다.
- 백분위수는 원시 샘플에서 계산한다. 구간 평균의 평균, 백분위수의 평균은 의미가 없다.
- 오류 응답은 빠르게 끝나서 지연 분포를 좋아 보이게 만든다. 오류율과 지연을 항상 같이 본다.

## 3. 병목은 자원으로 설명한다 (USE)
- 각 자원(CPU, 메모리, 커넥션 풀, 스레드 풀, 디스크, 네트워크)의 사용률·포화·오류를 본다.
- 클라이언트 측 지연 분해(연결 대기·연결·TLS·전송·서버 처리·수신)로 어느 쪽인지 먼저 좁히고,
  서버 측 자원 지표로 확인한다.
- 지연이 꺾인 시점에 함께 오른 자원 지표가 1순위 후보다. 상관은 후보를 고르는 도구이고, 확인은 조건을 바꾼 재실행이다.

## 4. 측정 자체를 의심한다
- 부하 생성기가 목표 도착률을 못 내면(누락 반복) 그 구간은 대상이 아니라 생성기의 한계다.
- 생성기와 대상이 같은 호스트면 서로 자원을 뺏는다. 한계로 적는다.
- 워밍업(JIT, 커넥션 풀, 캐시) 구간은 기준선과 분리한다.

## 5. 보고는 결정에 쓰이게
- 결론(SLO 충족 여부) → 핵심 수치 → 병목과 근거 → 한계 순서. 근거 없는 권고는 쓰지 않는다.
