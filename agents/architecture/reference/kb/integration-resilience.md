# KB: 통합과 복원력

## 리뷰 훅 (이걸 점검하라)
- [ ] 원격 호출(REST/RPC)에 **타임아웃**이 설정됐는가 — 무한 대기는 스레드 고갈·장애 전파의 시작.
- [ ] 반복 실패하는 호출에 **서킷브레이커**가 있는가 — 장애 서비스에 계속 호출해 연쇄 붕괴(cascading failure)를 막는가.
- [ ] **재시도**가 idempotent(멱등) 연산에만, 백오프와 함께 적용됐는가 — 비멱등 재시도는 중복 부작용.
- [ ] 동기 호출로 충분한가, **비동기(이벤트/메시징)** 가 더 적합한가 — 즉시 응답이 불필요하면 비동기로 결합을 낮춘다.
- [ ] 여러 서비스에 걸친 작업이 분산 트랜잭션 대신 **saga**(이벤트/오케스트레이션 + 보상 트랜잭션)로 처리되는가.
- [ ] 일관성 모델이 명시됐는가 — 비동기/이벤트는 **최종 일관성**을 전제하는데 강한 일관성을 가정한 코드가 없는가.
- [ ] 이벤트 소비가 **at-least-once** 전제에서 멱등/중복 처리(dedup)를 갖췄는가.

## 근거 (패턴 요지 — microservices.io)
- **동기 vs 비동기**: 동기(요청/응답, REST·gRPC)는 단순하지만 호출자가 응답까지 묶여 가용성·지연이 연쇄된다. 비동기(메시징·이벤트)는 송수신을 분리해 느슨한 결합·탄력성을 얻지만 흐름 추적·일관성이 복잡.
- **회복성 패턴**: **Timeout**(응답 한계), **Circuit Breaker**(연속 실패 시 호출 차단 후 점진 복구), **Retry**(일시 장애 재시도 — 멱등·백오프 필수). 이들이 없으면 한 느린 의존성이 전체를 끌어내린다.
- **데이터 일관성**: 서비스별 DB에서 다중 서비스 업데이트는 2PC 대신 **Saga**(일련의 로컬 트랜잭션 + 실패 시 보상 트랜잭션). 코레오그래피(이벤트 기반) 또는 오케스트레이션(중앙 조정).
- **이벤트 기반 일관성**: 이벤트로 상태를 전파하면 **최종 일관성**(eventual consistency)이 된다 — 읽기 측이 잠시 과거 상태를 볼 수 있음을 설계가 받아들여야 한다.
- **메시지 전달 보장**: 대개 at-least-once → 소비자는 멱등 처리·중복 제거 필요. CQRS/이벤트 소싱은 읽기/쓰기 분리와 이벤트 로그로 이를 보강.

## 트레이드오프
- 비동기/이벤트는 결합을 낮추고 확장에 유리하나, 디버깅·관측성·일관성 보장이 어렵다. 강한 일관성·단순 흐름이 필요하면 동기가 낫다. **호출 단위마다** 적합한 방식을 고르고, 동기를 쓸 땐 반드시 타임아웃+서킷브레이커로 격리한다.

## 인용 시
"microservices.io Reliability 패턴 기준, `OrderService`→`PaymentService` 동기 호출에 타임아웃/서킷브레이커 없음(`<path>`) → 연쇄 장애 위험. 타임아웃+서킷브레이커 적용, 즉시성 불필요하면 이벤트 비동기 전환(최종 일관성 수용) 권고" 식으로 근거와 함께 단다.
