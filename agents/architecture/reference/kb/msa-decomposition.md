# KB: 서비스 분해와 분산 모놀리스 (MSA)

## 리뷰 훅 (이걸 점검하라)
- [ ] 서비스가 **비즈니스 능력/서브도메인** 기준으로 나뉘었는가, 기술 레이어(별도 `*-controller`/`*-dao` 서비스)로 나뉘었는가.
- [ ] 각 서비스가 **자기 데이터를 소유**하는가 — 여러 서비스가 같은 DB/스키마/테이블을 직접 읽고 쓰면 **분산 모놀리스**(공유 DB 안티패턴).
- [ ] 서비스 간 **동기 호출 사슬**이 길고 강결합인가 — A→B→C 체인은 한 서비스 장애가 전체로 전파(시간적 결합).
- [ ] 서비스 경계를 가로지르는 **분산 트랜잭션**이 있는가 — 2PC 의존은 결합·취약성 신호. saga/이벤트로 대체 검토.
- [ ] 한 기능 변경이 **여러 서비스 동시 배포**를 강제하는가 → 독립 배포성 상실(분산 모놀리스 핵심 증상).
- [ ] 서비스 간 모델/계약이 **공유 라이브러리로 강결합**됐는가 — 공유 도메인 jar/패키지를 모든 서비스가 의존하면 변경이 전파.

## 근거 (요지)
- **분해 기준**: 마이크로서비스는 비즈니스 도메인(서브도메인/bounded context)을 따라 자른다. 기술 레이어로 자르면 하나의 변경이 여러 서비스를 건드린다.
- **정보 은닉·느슨한 결합**: 좋은 서비스는 내부를 숨기고 안정된 계약(API/이벤트)으로만 노출. 결합 유형 — 도메인/패스스루/공통/시간적 결합 중 **시간적(동기 호출 의존)·공통(공유 DB) 결합**을 가장 경계.
- **데이터 소유권**: 각 서비스가 자기 데이터베이스를 소유한다. **공유 DB**는 캡슐화를 깨고 독립 배포를 막는 대표 안티패턴(microservices.io: Shared database는 피하고 Database per Service).
- **분산 모놀리스**: 서비스로 쪼갰지만 강하게 결합돼 함께 배포해야 하는 상태 — 분산의 비용(네트워크·운영)만 떠안고 모놀리스의 결합은 그대로. MSA 도입의 최악 실패 모드.
- **통신**: 동기(요청/응답)는 단순하나 가용성·지연을 연쇄시킨다. 비동기(이벤트)는 느슨하지만 복잡성·최종 일관성을 받아들여야 한다(→ integration-resilience.md).

## 트레이드오프
- MSA는 독립 배포·독립 확장·기술 다양성을 얻지만 분산 시스템 복잡성(네트워크 신뢰성·관측성·데이터 일관성·운영 부담)을 치른다. **모놀리스/모듈러 모놀리스로 충분한지** 먼저 따진다 — 작은 팀·단순 도메인에 MSA는 과결합 비용만 늘릴 수 있다.

## 인용 시
"Building Microservices 데이터 소유권 기준, `OrderService`와 `PaymentService`가 동일 DB 스키마를 직접 접근(`<config/path>`) → 공유 DB 안티패턴, 분산 모놀리스. 서비스별 DB + 이벤트/API 통합 권고. 단, 트래픽·팀 규모가 작다면 모듈러 모놀리스가 더 적합할 수 있음" 식으로 근거·트레이드오프와 함께 단다.
