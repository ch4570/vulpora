# KB: 디자인 패턴 (헤드퍼스트 · GoF)

> 패턴은 **반복되는 설계 문제의 검증된 해법**이지 목표가 아니다. **문제가 실재할 때만** 적용하고,
> 항상 트레이드오프(간접화 비용 vs 확장성)를 명시한다. 과설계(패턴 강박)는 스멜이다.

## 설계 원칙 (헤드퍼스트 핵심)
- 변하는 것을 **캡슐화**하라(변경 격리).
- **상속보다 합성(composition)** — 행동을 위임으로 조립.
- **구현이 아니라 인터페이스에 프로그래밍**하라.
- **느슨한 결합**을 지향하라. **OCP**(확장 개방·변경 폐쇄). **DIP**(추상에 의존).

## 리뷰 훅
- [ ] **Strategy** — 알고리즘/정책이 분기(`when`)로 흩어지고 교체·확장이 잦다 → 전략 인터페이스 + 구현 주입.
- [ ] **Template Method / Template-Callback** — 작업 골격은 같고 일부 단계만 다르다(중복 골격) → 골격 고정 + 훅/콜백 분리(토비).
- [ ] **Factory Method / Abstract Factory** — `new`/구체 생성이 코드 곳곳에 흩어짐 → 생성 캡슐화.
- [ ] **Observer** — 상태 변화 시 여러 곳에 알려야 하고 구독자가 가변 → 발행/구독으로 결합 해소.
- [ ] **Decorator** — 조합 폭발하는 기능 추가를 상속으로 처리 중 → 동적 책임 추가(합성).
- [ ] **Adapter** — 인터페이스 불일치로 어댑팅 코드가 호출부에 산재 → 어댑터로 격리.
- [ ] **State** — 객체 동작이 상태에 따라 크게 다르고 상태 전이가 if로 엉킴 → 상태 객체로.
- [ ] **Facade** — 복잡한 서브시스템 호출 절차가 클라이언트에 노출 → 단순 진입점 제공.

## 안티패턴 (패턴 오용)
- 분기가 **거의 변하지 않는데** Strategy/State로 추상화(YAGNI 위반) → 단순 `when` 유지가 낫다.
- 한 구현뿐인데 인터페이스+팩토리 도입(추측성 일반화).
- 상속으로 충분/명확한데 Decorator 남발 → 가독성 저하.

## 인용 시
"헤드퍼스트 `Strategy` — 정책 교체축이 실재(사이트타입별)하므로 전략으로 분리" /
"GoF `Template Method` + 토비 템플릿-콜백으로 자원관리 중복 제거" 식으로.

## 적용 판단 체크 (적용 전 자문)
1. **변경/확장 축이 실재하는가?**(과거 변경 이력·예정된 케이스) — 없으면 보류.
2. 패턴 도입의 **간접화 비용**(클래스 증가·추적성)을 확장 이득이 정당화하는가?
3. 더 단순한 처방(Extract Function, sealed `when`)으로 충분하지 않은가?
