# KB: 객체지향 설계 (조영호 — 오브젝트 / 객체지향의 사실과 오해)

## 리뷰 훅
- [ ] **데이터 위주 설계인가?** 객체가 getter/setter 덩어리면 → **책임(행동)**을 객체 안으로(Tell, Don't Ask).
- [ ] **묻고 판단하는 코드(Ask)** — `if (obj.getX() > n) obj.setY(...)` → 객체에게 **메시지로 위임**.
- [ ] **빈약한 도메인 모델** — 서비스가 엔티티 데이터를 꺼내 모든 로직 수행 → 도메인 메서드로 이동.
- [ ] **캡슐화 위반** — 내부 컬렉션/상태가 그대로 노출(가변) → 읽기 전용 노출 + 변경은 메서드로.
- [ ] **잘못된 책임 배치** — 이 책임을 가진 데이터/협력자가 다른 객체에 있음 → **Move Function**.
- [ ] **의존성 방향** — 안정된 추상이 불안정한 구체에 의존하는가(DIP 위반) → 인터페이스 도입·역전.

## 핵심 개념
- **역할·책임·협력**: 협력(목표) → 역할(누가) → 책임(무엇을) → 메시지/메서드. 설계는 **책임 분배**가 핵심.
- **책임 주도 설계(RDD)**: "이 책임을 누가 지는 게 가장 자연스러운가"로 객체를 정한다. 데이터가 아니라 행동 먼저.
- **Tell, Don't Ask / 디미터 법칙**: 협력자의 내부를 묻지 말고 시켜라. 메시지 체인(`a.b().c().d()`)은 결합 신호.
- **캡슐화**: 변경 가능성이 높은 부분(구현)을 인터페이스 뒤로 숨겨 변경 파급을 막는다 = 자율적 객체.
- **다형성**: 조건 분기 대신 메시지에 대한 응답을 타입이 결정. 새 타입 추가로 확장(OCP).
- **SOLID**: SRP(단일 책임)·OCP(개방-폐쇄)·LSP(리스코프)·ISP(인터페이스 분리)·DIP(의존성 역전).

## 근거 (요지)
- "객체란 상태(데이터)가 아니라 **행동(책임)**으로 정의된다. 데이터는 책임을 수행하기 위한 수단일 뿐."
- "훌륭한 설계는 **변경에 유연**하다 — 캡슐화로 변경 파급을 국소화하고, 다형성으로 확장점을 연다."
- "협력이 객체의 행동을, 행동이 상태를 결정한다(상태→행동 순서가 아니다)."

## 인용 시
"『오브젝트』 책임 주도 설계 — 이 책임은 `Order`가 가져야 자연스럽다(데이터 보유자)" /
"Tell, Don't Ask 위반 → `member.discount(price)`로 위임" 식으로.

## 적용 순서 (빈약한 도메인 → 풍부한 도메인, 작은 단계)
1. 서비스에 흩어진 판단 로직 중 **한 덩어리**를 식별(특정 엔티티 데이터만 쓰는 코드).
2. 그 로직을 엔티티의 **의도 드러내는 메서드**로 **Extract + Move**(예: `order.canCancel()`).
3. 서비스는 위임 호출로 교체. 영속성 불변식(식별자/연관 일관성)은 유지. 매 단계 테스트.
