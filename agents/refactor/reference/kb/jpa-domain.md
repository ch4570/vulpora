# KB: JPA · 영속성 구조 (김영한)

> 리팩터링 관점: 영속성 기술 누수·빈약한 엔티티·연관관계 설계 스멜을 다룬다. **행위 보존**이 원칙이므로
> 쿼리 결과·트랜잭션 의미를 바꾸지 않는 선에서 구조만 개선한다(동작 변경은 분리).

## 리뷰 훅
- [ ] **빈약한 엔티티(setter 떡칠)** — 서비스가 setter로 상태를 조립 → 의도 드러내는 **도메인 메서드**로(예: `order.cancel()`). 불변식은 엔티티가 지키게.
- [ ] **N+1 / 즉시로딩 남용** — 연관을 루프에서 개별 조회 → fetch join / `@BatchSize` / 조회 전용 DTO. (성능 동작이 바뀌면 별도 변경으로 표기)
- [ ] **양방향 연관 편의 메서드 부재** — 양쪽 일관성을 호출부가 수동 관리 → 연관관계 편의 메서드로 캡슐화.
- [ ] **엔티티를 그대로 컨트롤러까지 노출** — 영속성 모델이 API 계약과 결합 → DTO 매핑으로 분리.
- [ ] **트랜잭션 밖 지연로딩(LazyInitializationException 위험)** — 경계 재배치(동작 영향 주의 → 분리 보고).
- [ ] **도메인이 `@Repository`/EntityManager에 직접 의존** — 포트(인터페이스)로 역전(DIP).

## 핵심 개념
- **객체 그래프 탐색**: 연관은 FK 추적이 아니라 객체 참조로 사고(`order.member.name`).
- **영속성 컨텍스트**: 1차 캐시·변경 감지(dirty checking)·쓰기 지연. 구조 변경이 이 의미를 깨지 않게.
- **연관관계 주인**: 외래키 소유 측이 주인. 편의 메서드로 양방향 일관성 유지.
- **도메인 모델 vs 빈약한 모델**: JPA 엔티티도 행위를 가질 수 있다 — 단, 영속성 불변식 우선.

## 인용 시
"『자바 ORM 표준 JPA』 — 빈약한 엔티티의 setter 조립을 `order.cancel()` 도메인 메서드로(불변식 캡슐화)" /
"연관관계 편의 메서드로 양방향 일관성 캡슐화" 식으로.

## 주의 (행위 보존)
- fetch 전략·쿼리 변경은 **결과/성능 동작을 바꿀 수 있다** → 순수 리팩터링이 아니라 **별도 변경**으로 분리·표기.
- 엔티티 메서드화는 동작 동일성을 테스트로 잠근 뒤 진행.
