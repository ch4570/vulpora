# KB: 동작 성격 → 다이어그램 타입

## 리뷰 훅 (이걸 점검하라)
- [ ] 1차 타입을 **하나** 골랐는가(억지로 한 타입에 끼워맞추지 않았는가).
- [ ] 고른 타입이 동작의 **핵심 성격**과 맞는가(아래 신호 표로 확인).
- [ ] 두 관점이 진짜 필요할 때만 다이어그램 2장으로 나눴는가(과적재 회피).

## 선택 신호 (동작 → 타입)

| 동작의 핵심 | 타입 | 신호 |
|-------------|------|------|
| 한 단위(함수/메서드) 내부의 **분기·루프·예외 처리** | **flowchart** | `if/when/switch`, 반복, early-return, try/catch, 가드 절이 많다 |
| 여러 **컴포넌트 간 호출 순서·협력**(동기/비동기, 요청/응답) | **sequenceDiagram** | Controller→Service→Repository→외부, 메시지 주고받음, 호출 깊이·시간순이 중요 |
| 하나의 **상태값이 단계를 옮겨다님**(수명주기) | **stateDiagram-v2** | enum 상태 필드, "PENDING→PAID→SHIPPED", 상태 전이 규칙이 핵심 |

## 보조 판단
- **데이터 변환 파이프라인**(A→B→C 단계 변환): flowchart `LR`로 단계 나열이 읽기 좋다.
- **여러 객체의 책임 분담을 한 흐름에서**: sequence가 "누가 무엇을"을 가장 잘 보여준다.
- **분기가 상태에 종속**(상태마다 다른 처리): state로 상태를 먼저 보이고, 복잡한 상태 내부는 flowchart로 하위 분리.

## 안티패턴 (하지 말 것)
- 모든 걸 flowchart 하나에 — 컴포넌트 협력까지 flowchart로 그리면 화살표가 얽힌다. 협력은 sequence로.
- sequence에 내부 분기를 과하게 — 한 참여자 내부의 깊은 `if` 트리는 flowchart로 따로 뺀다.
- 상태가 2개뿐인데 stateDiagram — 그냥 flowchart 분기로 충분하다(YAGNI).

## 2장 분리 기준
- 동작이 "컴포넌트 협력 + 특정 단계의 복잡한 내부 분기"를 둘 다 가지면:
  - 1장: sequence(전체 협력) — 복잡한 단계를 한 메시지로 표시.
  - 2장: flowchart(그 단계 내부 분기) — sequence의 해당 메시지를 진입점으로.
  - 두 장의 노드/메시지를 앵커 범례로 연결한다(같은 `파일:라인`이면 동일 코드임이 드러남).

## 인용 시
"동작 핵심이 컴포넌트 협력이므로 sequenceDiagram 선택(내부 분기는 flowchart로 분리)" 식으로 근거를 단다.
