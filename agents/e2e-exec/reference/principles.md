# E2E 테스트 실행 핵심 원칙 (Principles)

> 이 문서는 E2E 실행·테스트 데이터 관리의 실무 원리를, **공식 문서와 업계 표준 글**로 검증·보정한
> 원칙 모음이다. 에이전트와 스킬이 판단의 근거로 삼는 "헌법" 역할을 한다.
>
> **출처(Sources)**
> - Playwright 공식 문서 — 실행/대기/재시도/픽스처/trace (playwright.dev/docs)
> - Google Testing Blog — flaky 테스트, 테스트 크기/격리 (testing.googleblog.com)
> - Martin Fowler, "Test Double" 및 테스트 데이터 관리 실무 — 격리·설정·정리 (martinfowler.com)
>
> KB는 "사실·규칙", principles는 "통찰·판단 기준". **충돌 시 KB(공식 문서)가 우선**한다.

---

## 0. 대전제: 실행은 흔적을 남기지 않는다

- E2E 실행의 완료 조건은 "테스트가 통과했다"가 아니라 **"통과했고 환경이 원상복구되었다"**이다.
- 테스트가 만든 데이터·세션·검색 인덱스 문서·메시지는 **반드시 정리**한다. 정리 누락은
  다음 실행을 오염시키고 환경을 고아 데이터로 채우는 **버그**다(불완전 실행).

---

## 1. 격리 (Isolation) — 가장 중요한 원칙

1. **테스트별 고유 데이터.** 각 시나리오는 자기만의 데이터(고유 ID·전용 픽스처)로 동작한다.
   공유 데이터를 여러 테스트가 변경하면 순서 의존·상호 오염이 생긴다.
2. **공유 가변 상태를 피하라.** 세션·DB 행·검색 인덱스·캐시처럼 공유되는 가변 상태는
   직렬 실행·전용 데이터로 충돌을 차단한다. 병렬 실행이 상태를 공유하면 결정성이 깨진다.
3. **운영/공유 환경 불가침.** 시드·정리는 격리된 픽스처·전용 환경에서만. 운영 데이터는 절대 대상이 아니다.

---

## 2. 테스트 데이터 라이프사이클 — setup → execute → verify → cleanse

4. **시드(setup).** 무엇을 생성/변경하는지 **기록**한다(생성 ID·인덱스 문서·토픽 메시지).
   이 기록이 정리의 입력이다.
5. **클렌징(teardown) 방식 선택**:
   - **트랜잭션 롤백** — 트랜잭션 경계 안의 DB 변경은 롤백 한 번으로 깨끗하게 되돌린다(가장 싸고 안전).
   - **명시적 삭제** — 커밋되었거나 외부 시스템(검색 인덱스·메시지 토픽·캐시·파일)에 남은 변경은
     명시적 teardown으로 되돌린다(롤백이 닿지 않는 영역).
6. **멱등(Idempotent) 정리.** 정리는 여러 번 실행해도 안전해야 한다. 부분 실패·중단 후 재실행에도
   환경이 원상복구되어야 한다(이미 없는 리소스 삭제 시도는 무해해야 함).
7. **정리 검증.** teardown 후 생성 리소스가 실제로 사라졌는지 확인한다(카운트=시드 전 값, 잔여 0).
   검증되지 않으면 정리는 완료가 아니다.
8. **고아 데이터 방지.** 시드 시 기록한 리소스를 기준으로 빠짐없이 제거한다. 실행이 중단되어도
   다음 실행 시작 전 정리할 수 있도록 정리를 idempotent·재진입 가능하게 설계한다.

---

## 3. flaky 안정성 — 결정성으로 말한다

9. **flaky는 은폐가 아니라 격리한다.** 간헐 실패는 자동 재시도로 통과시키지 않는다. 격리(쿼런틴)하고
   원인을 분석해 QA에 보고한다. 조용한 재시도는 진짜 결함을 숨긴다(Google Testing Blog).
10. **결정적 대기.** 고정 `sleep`은 금지. UI/비동기는 **조건 기반 대기**(요소 가시성, 응답 도착,
    데드라인 폴링)로 기다린다. 고정 sleep은 느리면 깨지고 빠르면 낭비다(Playwright auto-wait).
11. **재시도 정책은 명시적으로.** 재시도가 필요하면 프레임워크의 재시도 설정으로 명시하고, 재시도로
    가려진 flaky는 별도 추적한다 — "통과처럼 보이게" 만드는 용도가 아니다.

---

## 4. 픽스처·환경 분리

12. **운영 절대 금지, 전용 환경만.** E2E는 격리된 환경(로컬 compose / 일회성 컨테이너)에서.
    픽스처는 setup/teardown을 캡슐화해 누수 없이 자원을 생성·정리한다(Playwright fixtures).
13. **외부 의존성은 모킹/스텁.** 제어 불가능한 외부 시스템은 테스트 더블로 대체해 결정성·격리를
    확보한다(Fowler, Test Double). 단, E2E의 핵심 경로는 실제 통합을 검증하는 것이 목적임을 유의.
14. **시드 데이터는 합성·라운드 값.** 실제 사용자/PII를 픽스처에 쓰지 않는다. 둥근 번호 ID 등 합성값만.

---

## 5. 아티팩트·재현성

15. **실패는 재현 가능한 증거와 함께.** 스크린샷·비디오·trace를 남겨 실패를 재현/디버그할 수 있게 한다
    (Playwright trace viewer). 성공 시 아티팩트는 최소화해 리포트를 가볍게.
16. **관찰한 것만 보고.** 결과는 추측이 아니라 증거로 말한다. run JSON·아티팩트가 SSOT.
17. **비밀·PII 마스킹.** 아티팩트·로그·리포트는 공유되므로 자격증명/민감정보를 마스킹한 뒤 기록한다.

---

## 6. 실행 규율 (스킬 규약 존중)

18. **자동감지.** 빌드시스템(gradle/maven/npm/pnpm/yarn)·E2E 프레임워크(Playwright 등)를 가정하지
    말고 마커 파일로 감지한다.
19. **무재시도·무자동폴백·직렬 실행** 규약을 우회하지 않는다.
20. **시나리오 설계 불가침.** 시나리오는 `qa-test-designer`가 SSOT. 실행자는 결함을 핸드오프할 뿐
    임의 수정하지 않는다.
