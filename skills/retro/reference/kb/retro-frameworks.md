# KB: 회고 프레임워크

회고는 정해진 기간(스프린트·릴리스·작업)을 돌아보며 **잘된 것·아픈 것·바꿀 것**을 끌어내는
구조화된 점검이다. 형식은 같은 목표를 다른 질문 프레임으로 묻는다.

## 대표 형식 (질문 프레임)

| 형식 | 컬럼 | 무엇을 끌어내나 |
|------|------|----------------|
| **Keep / Problem / Try** | 유지할 것 / 문제였던 것 / 다음에 시도할 것 | 균형 잡힌 일반 회고. `/retro` 기본 |
| **Start / Stop / Continue** | 시작할 것 / 멈출 것 / 계속할 것 | 행동(behavior) 중심, 액션 도출이 쉬움 |
| **4Ls** | Liked / Learned / Lacked / Longed for | 감정+학습, 부족했던 것·바랐던 것 분리 |
| **Mad / Sad / Glad** | 화났던 것 / 아쉬웠던 것 / 기뻤던 것 | 감정 기반, 팀 분위기·번아웃 신호 포착 |
| **DAKI** | Drop / Add / Keep / Improve | 프로세스·도구 정리에 적합 |
| **Sailboat** | 바람(추진) / 닻(방해) / 암초(위험) / 섬(목표) | 비유 기반, 목표·리스크 시각화 |

## 어떤 형식을 언제 쓰나

- **일반 작업/세션 회고** → Keep/Problem/Try (단순·균형).
- **행동을 바꾸고 싶을 때** → Start/Stop/Continue (액션이 컬럼에서 바로 나옴).
- **팀 사기·갈등이 의심될 때** → Mad/Sad/Glad, 4Ls (감정 표면화).
- **프로세스·도구 정리** → DAKI.
- **같은 형식을 반복하면 답이 형식화**된다 — 가끔 형식을 바꿔 새 시각을 얻는다.

## 좋은 회고의 5단계 (Esther Derby & Diana Larsen 모델)

1. **무대 설정(Set the stage)** — 범위·기간·규칙(비난 없음) 명시.
2. **데이터 수집(Gather data)** — 사실·이벤트·지표를 모은다(타임라인, git log).
3. **통찰 도출(Generate insights)** — "왜 이런 일이?" 패턴·원인 분석.
4. **행동 결정(Decide what to do)** — SMART 액션 아이템 1~2개로 좁힌다.
5. **마무리(Close)** — 회고 자체를 회고하고 다음으로 연결.

## 스크럼 회고

Scrum Guide(2020): 스프린트마다 Sprint Retrospective를 열어 사람·관계·프로세스·도구를
점검하고, 개선 항목을 다음 스프린트 백로그에 넣는다. 타임박스를 둔다.

## 리뷰 훅

- [ ] 회고 범위·기간이 명확히 정해졌는가(무엇을 돌아보는가).
- [ ] "비난 없음" 규칙을 무대 설정에서 명시했는가.
- [ ] 사실 수집(데이터) 단계를 통찰·행동보다 먼저 했는가.
- [ ] 형식이 이번 목적에 맞는가(감정 점검 vs 프로세스 정리 vs 일반 점검).
- [ ] 통찰이 막연한 소감이 아니라 구체적 패턴·원인으로 정리됐는가.
- [ ] 회고가 추적 가능한 액션 1~2개로 수렴했는가(너무 많이 벌이지 않았는가).
