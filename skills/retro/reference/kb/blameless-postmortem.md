# KB: 비난 없는 포스트모템 (Blameless Postmortem)

포스트모템은 사고(incident)·장애의 영향, 원인, 대응, 재발 방지 행동을 기록하는 문서다.
핵심 전제는 **비난 없음(blameless)**: 사람이 아니라 시스템과 프로세스를 본다.

## 왜 비난 없음인가

- 사람을 탓하면 사람들은 문제·실수를 **숨긴다** → 진짜 원인이 묻히고 재발한다.
- 어떤 행동이 사고로 이어졌다면, 그 시점에는 그 행동이 **합리적으로 보였다**고 가정한다.
  "왜 그게 합리적으로 보였는가"를 물으면 시스템의 결함(부족한 가드레일·문서·경고)이 드러난다.
- 목표는 처벌이 아니라 **학습과 시스템 개선**이다.

## 심리적 안전 (psychological safety)

- 보복·창피 없이 실패를 드러낼 수 있어야 솔직한 데이터가 모인다.
- 리더가 자신의 실수를 먼저 공유하면 안전이 커진다.
- "포스트모템 작성 = 벌"이 되면 사람들이 트리거를 회피한다 — 이는 문화 실패다.

## 포스트모템 문서가 담는 것

| 섹션 | 내용 |
|------|------|
| 요약(Summary) | 무슨 일이, 얼마나, 언제 |
| 영향(Impact) | 사용자/시스템/비즈니스 영향, 지속 시간 |
| 타임라인(Timeline) | 시각별 사실(탐지·대응·복구) — 증거 기반 |
| 근본/기여 원인 | 단일 원인 강박 금지, 기여 요인 함께 |
| 무엇이 잘됐나 | 빠른 탐지, 효과적 롤백 등(Keep) |
| 무엇이 안 됐나 | 지연·오판 등(Problem) |
| 운(luck) | 우연히 막힌 더 큰 피해 |
| 액션 아이템 | 소유자·기한·검증 기준 (KB: action-item-tracking) |
| 교훈(Lessons) | 재사용 가능한 인사이트 |

## 포스트모템 작성 트리거 (사전 정의)

조직이 미리 합의한 임계값에서 작성한다. 예:

- 사용자 가시적 다운타임·성능 저하가 임계 초과.
- 어떤 종류든 **데이터 손실**.
- 온콜 엔지니어의 개입이 필요했던 사고.
- 해결 시간이 임계 초과.
- **모니터링이 잡지 못한** 장애(사람이 먼저 발견).

> 트리거는 명확·객관적이어야 한다. 모호하면 "이건 포스트모템감인가" 논쟁으로 회피된다.

## 포스트모템 ≠ 회고

- 회고(retrospective)는 정기 주기(스프린트)에 **잘된 것·바꿀 것**을 폭넓게 본다.
- 포스트모템은 특정 **사고**를 깊게 파고 재발 방지에 집중한다.
- `/retro`는 둘의 정신(비난 없음·사실 우선·액션 도출)을 작업 단위에 적용한 형태다.

## 리뷰 훅

- [ ] 문서가 사람 이름을 탓하는 표현 없이 시스템·프로세스 언어로 쓰였는가.
- [ ] 타임라인이 증거(로그·커밋·시각)에 근거하는가.
- [ ] "잘된 것"과 "운"도 기록했는가(개선 포인트와 강화 포인트 모두).
- [ ] 각 원인이 액션 아이템(소유자·기한)으로 연결됐는가.
- [ ] 작성 트리거가 사전 정의 기준을 충족하는가(작성 자체가 처벌처럼 쓰이지 않는가).
- [ ] 문서가 팀에 공유·검토되어 학습 자산이 되는가.
