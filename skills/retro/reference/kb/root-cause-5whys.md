# KB: 근본원인 분석 / 5 Whys

5 Whys는 표면 증상에서 출발해 "왜?"를 반복하며 더 깊은 원인으로 내려가는 기법이다.
숫자 5는 경험칙이며 더 적거나 많을 수 있다.

## 기본 절차

1. **문제 진술**을 한 문장으로 명확히 적는다(증상, 사실 기반).
2. "왜 이 일이 일어났나?"를 묻고 답을 적는다.
3. 그 답에 다시 "왜?"를 묻는다.
4. 더 깊은 원인이 나오지 않을 때까지 반복(보통 5회 내외).
5. 마지막 답이 **고칠 수 있는 시스템·프로세스 원인**이면 멈춘다.

### 예시 (일반 엔티티 `Order` 처리)

- 문제: 야간 배치에서 `Order` 적재 작업이 실패했다.
- 왜? → 입력 파일이 비어 있었다.
- 왜? → 업스트림 추출 잡이 산출물을 만들지 못했다.
- 왜? → 추출 잡이 조용히 실패했고 알림이 없었다.
- 왜? → 그 잡에 실패 경보가 설정돼 있지 않았다.
- 왜? → 잡 추가 시 경보 설정이 체크리스트에 없었다. ← **시스템 원인(고칠 수 있음)**

## 함정 (반드시 인지)

- **단일 근본원인 과단순화**: "왜?"를 한 줄기로만 따라가면 다른 기여 요인을 놓친다. 복잡한
  사고는 보통 **여러 원인의 결합**이다 → 한 단계에서 답이 둘 이상이면 가지를 나눠 본다.
- **사람 탓에서 멈춤**: "담당자가 실수했다"는 근본원인이 아니다. "왜 그 실수가 가능했나
  (가드레일·리뷰·자동화 부재)"로 더 내려간다(KB: blameless-postmortem).
- **추측을 사실처럼**: 각 "왜"의 답은 증거로 뒷받침돼야 한다. 근거 없으면 "가설"로 표기하고
  검증 액션을 만든다(KB: timeline-evidence).
- **너무 일찍 멈춤 / 너무 깊이 파기**: 통제 불가능한 외부 요인(천재지변 등)까지 내려가면
  실행 불가. **고칠 수 있는 가장 깊은 지점**에서 멈춘다.

## 기여 원인 vs 근본 원인

- **근본 원인(root cause)**: 제거하면 이 부류의 문제가 재발하지 않게 만드는 원인.
- **기여 원인(contributing factor)**: 사고를 악화·가능하게 했지만 단독으로 충분치 않은 원인.
- 둘 다 기록하고, 각각에 대응 액션을 둔다. 근본원인 하나만 고치고 끝내지 않는다.

## 다른 기법과의 관계

- 5 Whys는 가볍고 빠르다. 더 복잡한 사고는 Fishbone(Ishikawa) 다이어그램, Fault Tree,
  Causal Map 등으로 다중 원인을 시각화할 수 있다.

## 리뷰 훅

- [ ] 문제 진술이 증상(사실)으로 명확히 적혔는가.
- [ ] 각 "왜"의 답이 증거로 뒷받침되는가(추측은 가설로 표기).
- [ ] 분석이 "사람 실수"에서 멈추지 않고 시스템 원인까지 내려갔는가.
- [ ] 단일 원인으로 과단순화하지 않고 기여 요인을 함께 봤는가.
- [ ] 멈춘 지점이 **고칠 수 있는** 원인인가(통제 불가 요인이 아닌가).
- [ ] 각 원인이 대응 액션 아이템으로 연결됐는가.
