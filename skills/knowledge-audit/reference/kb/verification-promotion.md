# KB: 검증과 승급/폐기/보류

## 1. 검증가능성 원칙 (Verifiability)

Wikipedia 핵심 정책 "Verifiability"의 요지: **"진실이라고 믿는 것"이 아니라 "신뢰 가능한 출처로 검증 가능한 것"만 실린다.** 입증 책임(burden of evidence)은 **추가/유지하려는 쪽**에 있다.

KB 큐레이션에 적용하면:

- 후보가 **참처럼 보이는 것만으로는 부족**하다 — 근거(ground truth)로 **대조 가능**해야 승급한다.
- 입증 책임은 **승급하려는 큐레이터**에게 있다. 근거를 못 대면 승급하지 않는다.
- "맞을 것 같다"는 추정 승급 금지.

## 2. 근거(ground truth)와 증거 요건

지식 유형별로 "신뢰 가능한 출처"가 다르다.

| 후보 유형 | 근거(ground truth) | 증거 요건 |
|-----------|--------------------|-----------|
| 코드 구조/경로/심볼 단정 | 현재 코드베이스 | `grep`/`Glob`으로 파일·심볼 **현존 실증** |
| 동작/계약 단정 | 코드 + 이력 | 코드 경로 + 필요시 git 이력 |
| 기술 일반 사실 | 공식 문서/표준 | `source` URL 인용 |

- 후보의 `evidence` 헤더가 **실제 근거를 가리키는지** 대조한다(헤더만 있고 근거 부재면 미검증).
- 증거가 코드와 **어긋나면**(파일/심볼 부재) 거짓으로 판정 → 폐기.

## 3. 삼분 결정 (promote / discard / hold)

| 판정 | 조건 | 조치 |
|------|------|------|
| **승급(promote)** | 참 + 코드 실증 일치 + 정본에 없음(중복 아님) + 재사용 가치 | 정본 KB로 편입 + 인덱스 추가 + 출처/날짜 기록 + 원본 삭제 |
| **폐기(discard)** | 코드와 어긋남 · 정본/규약과 중복 · 사소함 · 틀림 | 후보 레인에서 삭제(자율) |
| **보류(hold)** | 아직 검증 불가(맥락 부족) | 그대로 둠, 다음 패스에서 재판정 |

- 4요건(참·실증·비중복·재사용)을 **모두** 충족해야 승급. 하나라도 빠지면 폐기 또는 보류.
- 확신 없으면 **폐기보다 보류** — 거짓 폐기보다 판단 유보가 안전(살아남으면 신뢰도↑).

## 4. 패스당 승급 한도 (per-pass limit)

- 한 감사 패스의 승급은 **소수로 제한**(예: ≤ 3건). 대량 승급은 검증 부실의 신호.
- 한도를 두는 이유: 각 승급은 정본을 오염시킬 수 있으므로 **신중히, 검증 가능한 만큼만**.
- 폐기·보류에는 한도가 없다(정본을 늘리지 않으므로 리스크가 낮다).
- 승급은 git에 남으므로 잘못되면 `git revert`로 되돌린다(`audit-checklist-cadence.md`).

## 리뷰 훅

- [ ] 승급 후보가 **근거로 검증 가능**한가("참처럼 보임"이 아니라 실증).
- [ ] 코드 단정은 `grep`/`Glob`으로 **파일/심볼 현존을 실증**했는가.
- [ ] 후보의 `evidence` 헤더가 **실제 근거**를 가리키는가.
- [ ] 승급은 **4요건(참·실증·비중복·재사용)** 을 모두 충족하는가.
- [ ] 확신 없는 항목을 **폐기하지 않고 보류**로 처리했는가.
- [ ] 한 패스 승급이 **한도(예: ≤3건)** 안에 있는가.
