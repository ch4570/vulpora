# KB: 정기 KB 감사 체크리스트와 주기

## 1. 왜 정기 감사인가 (Google docguide)

Google "Documentation Best Practices"의 핵심: **"문서는 코드처럼 관리하라(Treat documentation like code)."** 코드가 변하면 문서가 썩으므로(stale), **소유자·갱신·정리**가 지속돼야 한다. KB도 동일 — 자동 적재 레인은 감사 없이 두면 노후·중복·오류로 썩는다.

## 2. 감사 절차 (inventory → triage → apply)

### 단계 1: 인벤토리(inventory)

- 후보 레인의 항목을 **나열**한다(예: `ls auto/*.md`). 비어 있으면 종료.
- 전처리(필수): **레인 계약/provenance 포맷**과 **정본 인덱스**를 먼저 읽는다(중복 차단).

### 단계 2: triage 삼분 (promote / discard / hold)

각 후보를 세 축으로 판정한다(상세: `verification-promotion.md`).

| 판정 | 한 줄 기준 |
|------|-----------|
| 승급 | 참 + 코드 실증 + 비중복 + 재사용 가치 |
| 폐기 | 코드와 어긋남 · 중복 · 사소 · 틀림 |
| 보류 | 검증 불가(맥락 부족) → 다음 패스 |

### 단계 3: 반영(apply)

- **폐기**: 후보 삭제 + 레인 인덱스에서 해당 줄 제거(자율).
- **승급**: 정본 KB로 편입 + 정본 인덱스 추가 + 출처/날짜 기록 + 원본 삭제.
- 쓰기 범위는 **지식 디렉터리 안으로만** — 규약 문서(AGENTS.md)·스킬·에이전트는 건드리지 않는다.

## 3. 임계치와 배치 한도 (thresholds & batch limits)

| 항목 | 권장 | 이유 |
|------|------|------|
| 감사 트리거 | 후보 누적이 임계치 초과 시 | 무인 트리거(사람 대기 제거) |
| 패스당 승급 한도 | ≤ 소수(예: 3건) | 정본 오염 최소화 |
| 폐기/보류 한도 | 없음 | 정본을 늘리지 않아 저위험 |

- 트리거를 **사람이 아니라 누적 임계치(사건 기반)** 에 묶으면 감사 누락이 줄어든다.
- 한 번에 다 처리하려 하지 말고 **배치**로 — 검증 가능한 만큼만.

## 4. 롤백 안전 (rollback safety)

- 모든 변경은 **git에 기록**되어 되돌릴 수 있어야 한다(`git revert`, 후보 일괄 삭제 등).
- 안전장치는 **사람 승인이 아니라 (1) 코드 실증 게이트 + (2) git 추적 + (3) 롤백 용이성** 세 가지다.
- 잘못된 승급이 발견되면 즉시 되돌리고, 같은 오류를 **폐기 규칙**으로 반영한다.
- 빌드/검증 게이트가 있는 저장소라면 감사 후에도 **빌드시스템 자동감지**(gradle/maven/npm/pnpm/yarn) 게이트가 통과하는지 확인한다(특정 도구에 고정하지 않는다).

## 리뷰 훅

- [ ] 감사 전 **전처리**(레인 계약 + 정본 인덱스)를 읽었는가.
- [ ] 인벤토리 → triage(삼분) → 반영 **순서**를 지켰는가.
- [ ] 쓰기 범위가 **지식 디렉터리 안**으로 한정됐는가(규약/스킬 불변).
- [ ] 패스당 승급이 **배치 한도** 안에 있는가.
- [ ] 모든 변경이 **git으로 롤백 가능**한가.
- [ ] 감사 트리거가 **누적 임계치(사건 기반)** 에 묶여 있는가.
