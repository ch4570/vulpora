# KB: 노후와 신선도

## 1. 날짜 메타데이터 (Dublin Core 기반)

Dublin Core(DCMI Terms)는 자원의 시간 속성을 별도 항목으로 분리한다. KB도 동일하게 **생성·검증·갱신 시점**을 따로 기록한다.

| DCMI term | KB 필드 | 의미 |
|-----------|---------|------|
| `dcterms:created` | (암묵) 파일 생성 | 항목이 처음 기록된 시점 |
| `dcterms:date` / `dcterms:issued` | `last_fetched` | 출처를 마지막으로 가져온/확인한 날 |
| `dcterms:modified` | `last_verified` | 코드/현실과 마지막으로 대조해 참임을 확인한 날 |
| `dcterms:valid` | (선택) 만료 정책 | 유효 기간 또는 재검증 기한 |

> **핵심 구분**: `last_fetched`(출처를 본 날) ≠ `last_verified`(사실임을 확인한 날).
> 출처를 다시 읽기만 해도 신선해 보이지만, **실제로 검증한 날**이 신뢰의 기준이다.

```yaml
---
title: ...
source: https://...
last_fetched: 2026-06-24      # 출처 확인일
last_verified: 2026-06-24     # 코드/현실 대조 통과일 (선택, 정본 권장)
---
```

## 2. 재검증 주기 (re-validation cadence)

항목 종류에 따라 재검증 빈도를 달리한다. **변동성이 높을수록 짧게.**

| 항목 유형 | 권장 재검증 주기 | 근거 |
|-----------|------------------|------|
| 코드 구조/파일 경로 의존 | 잦음(릴리스·리팩터마다) | 코드가 자주 바뀜 |
| 공식 문서/표준 distill | 메이저 버전 변경 시 | 안정적 |
| 운영 절차·정책 | 정책 개정 시 | 사건 기반 |

- 주기는 **고정 일수보다 사건(코드 변경·문서 개정)에 묶는 편**이 누락이 적다.
- 정기 감사(`audit-checklist-cadence.md`)가 재검증의 실행 지점이다.

## 3. 노후(rot) 탐지 신호

지식이 썩었음을 의심해야 하는 신호:

- 참조하는 **파일/심볼/경로가 더 이상 존재하지 않음**(`grep`/`Glob` 미스).
- `last_verified`가 오래됐는데 그 사이 관련 모듈이 변경됨(git 이력 대조).
- 같은 주제의 **더 새로운 정본 항목과 내용이 충돌**.
- 출처 URL이 죽었거나(404) 문서가 개정되어 단정의 근거가 사라짐.

## 4. 만료 정책 (expiry policy)

- 노후 의심 항목은 **즉시 삭제하지 말고 상태 전이**시킨다: 정본 → 보류(재검증 필요) 표시.
- 코드 실증으로 **거짓임이 확인되면** 폐기. 단지 오래됐다는 이유만으로는 폐기하지 않는다.
- 만료 임박 항목은 다음 감사에서 우선 triage 대상으로 올린다.
- 폐기 시에도 git 이력에 남으므로 복구 가능(`git revert`).

## 리뷰 훅

- [ ] 각 항목에 `last_fetched`(출처 확인일)가 있는가.
- [ ] 정본 항목에 `last_verified`(사실 확인일)가 별도로 있는가.
- [ ] 참조 파일/심볼/경로가 **현존**하는가(노후 탐지: `grep`/`Glob`).
- [ ] `last_verified` 이후 관련 모듈이 변경됐는가(git 이력 대조).
- [ ] 출처 URL이 살아 있고 단정의 근거가 여전히 유효한가.
- [ ] 노후 항목을 **즉시 폐기**하지 않고 재검증/보류로 먼저 처리하는가.
