# KB: 안전한 리팩터링 절차 (Fowler ch.1-2)

> "리팩터링이란 무엇이고, 어떻게 안전하게 하는가". 다른 KB가 *무엇을 바꿀지*라면, 이 문서는
> *깨지지 않게 바꾸는 절차*를 다룬다.

## 정의
- **리팩터링(명사)**: 동작을 바꾸지 않으면서 구조를 개선하는, **이름 붙은 작은 변환** 하나.
- **리팩터링(동사)**: 그런 변환의 연속으로 코드를 개선하는 활동.
- 관찰 가능한 동작(입출력·부수효과·계약)을 바꾸면 리팩터링이 아니라 **기능 변경**이다.

## 두 개의 모자 (Two Hats)
| 모자 | 하는 일 | 테스트 |
|------|---------|--------|
| 기능 추가 | 동작/기능을 바꾸거나 추가 | **새 테스트 추가** |
| 리팩터링 | 구조만 개선, 동작 불변 | 테스트 추가 X, **기존 테스트 그대로 통과** |
- 두 모자를 **한 커밋에 섞지 않는다**. 섞이면 리뷰·롤백·원인 추적이 불가능.

## 작은 단계 (Small Steps)
- 변환 → 컴파일 → 테스트 → 커밋(또는 다음 변환). 깨지면 **직전 한 단계만** 의심·되돌림.
- 큰 변경은 작은 변환의 합으로 분해(Split Phase, Extract→Move→Inline 조합).

## 테스트 안전망 / 특성화 테스트
- **자가 테스트 코드(self-testing code)** 가 리팩터링의 전제(ch.4). 빠르고 결정적인 테스트일수록 안전망이 강하다.
- 테스트가 없는 레거시는 먼저 **특성화 테스트(characterization test)** 로 *현재* 동작(올바르든 아니든)을 고정한 뒤 리팩터링한다.
- 버그를 발견해도 리팩터링 중에는 고치지 않는다(모자 분리). 별도로 기능 모자에서 처리.

## 검증 실행 — 빌드시스템 자동 감지
- 빌드툴을 하드코딩하지 않는다. 레포에서 **자동 감지**: gradle / maven / npm / pnpm / yarn.
  - 감지 신호 예: `build.gradle(.kts)`/`gradlew` → gradle, `pom.xml` → maven,
    `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `package-lock.json` → npm.
- 각 변환 후 해당 빌드툴의 **테스트 타깃**을 돌려 그린을 확인하고 다음 단계로.

## 가치 ÷ 위험 우선순위
- 곧 손댈 코드·자주 읽히는 코드·버그가 모이는 코드부터. 이해/수정 비용 절감(가치)이
  깨질 위험·테스트 부재(위험)를 넘을 때만 진행.
- **기회적 리팩터링(보이스카우트 규칙)**: 기능 작업하러 들른 김에 주변을 조금 정리하고 나온다.
  단 작업 범위를 넘는 산만한 확산은 통제한다.

## 언제 리팩터링하지 않는가
- 재작성이 더 싼 엉망 코드, 곧 폐기될 코드.
- 테스트 안전망을 만들 수 없고 위험이 가치를 압도할 때(우선 안전망부터).
- 두 모자를 분리할 여유가 없을 때(마감 직전) → 멈추고 기술부채로 기록.

## 리뷰 훅
- [ ] 이 변경은 동작을 보존하는가, 아니면 기능 변경인가(모자 구분).
- [ ] 기능 변경과 리팩터링이 **한 커밋/PR에 섞이지** 않았는가.
- [ ] 리팩터링 대상에 통과하는 테스트 안전망이 있는가. 없으면 특성화 테스트를 먼저 깔았는가.
- [ ] 변경이 작은 단계로 쪼개졌고, 각 단계마다 빌드·테스트가 그린인가.
- [ ] 검증을 레포의 **실제 빌드시스템(자동 감지)** 으로 돌렸는가(가정/하드코딩 아님).
- [ ] 이 리팩터링의 **가치 ÷ 위험**이 정당한가(곧 손댈/자주 읽힐 코드인가).
- [ ] 범위가 작업 의도를 넘어 산만하게 확산되지 않았는가.
