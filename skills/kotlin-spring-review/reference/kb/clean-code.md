# Clean Code 원칙 — 코드 리뷰 체크 (Kotlin/Spring 적용)

> 근거: Robert C. Martin, 「Clean Code」(클린 코드). 장별 원칙을 Kotlin/Spring 리뷰 체크로 변환.

## 2장 — 의미 있는 이름
- 🟡 의도를 드러내는 이름. 주석이 필요하면 이름이 실패한 것. (R2.1)
- 🟢 노이즈 단어 금지: `Info`, `Data`, `Manager`, `Processor`, `Helper`, `Util`, 숫자 시리즈(`a1,a2`). (R2.3/R2.8)
- 🟡 매직 리터럴 → `const val`/`enum`. 검색 가능한 이름. (R2.5) → 17장 G25와 동일.
- 🟢 인코딩 금지: 헝가리안, `m_` 접두사, 인터페이스 `I` 접두사. (R2.6)
- 🟡 한 개념엔 한 단어 — `fetch`/`retrieve`/`get` 혼용 금지, 같은 연산은 같은 동사. (R2.9)
- 🟡 클래스=명사, 메서드=동사. 솔루션/문제 도메인 용어(DDD 유비쿼터스 언어)와 일치. (R2.8/R2.11)

## 3장 — 함수 (리뷰에서 가장 빈번)
- 🟡 **작게, 한 가지만.** 함수에서 의미 있는 다른 함수를 추출할 수 있으면 한 가지 이상 하는 것. (R3.1/R3.2)
- 🟡 한 함수의 문장은 **같은 추상화 수준**. 오케스트레이션과 `sb.append("\n")`를 섞지 말라. (R3.3) → G34
- 🟠 **플래그(boolean) 인자 금지** — 함수가 두 가지 일을 한다는 신호. 함수 분리. (R3.8) → F3
- 🟡 인자 최소화: 0~2 이상적, 4개+ → `data class` 파라미터 객체. (R3.7) → F1
- 🟠 **명령과 조회 분리** — `fun set(...): Boolean` 같이 하는+답하는 함수 금지. (R3.10)
- 🟠 오류 코드 반환 대신 예외. `try/catch` 본문은 별도 함수로 추출(오류 처리도 한 가지). (R3.11)
- 🟠 **부수 효과 금지** — 이름에 없는 숨은 상태 변경(세션 초기화, 캐시, DB 쓰기). (R3.13) → N7
- 🟡 함수 길이 ~20~30줄 초과, 중첩 2단계 초과 → 분해 검토.

## 4장 — 주석
- 🟢 나쁜 코드에 주석 달지 말고 코드를 고쳐라. 진실은 코드에 있다. (R4.1)
- 🟡 **주석 처리된 코드 삭제** — VCS가 기억한다. (R4.6) → C5
- 🟢 변경 이력/작성자 주석 금지(git 사용), 시그니처 반복하는 KDoc 금지, 닫는 괄호 주석 금지. (R4.4)
- 🟡 KDoc은 진짜 공개 API에만. 내부/private 강제 문서화 금지.
- 🟠 빈 `catch`를 모호한 주석으로 변명 금지 → 실제 처리 요구.

## 5장 — 형식
- 🟡 파일은 짧게(대부분 ≤200줄, 최대 ~500). 신문처럼 위→아래 추상화 하강. (R5.2/R5.3)
- 🟢 ktlint/Detekt/`.editorconfig`로 자동화. 변수는 사용처 근처 선언. 호출자→피호출자 순서. (R5.5/R5.6)
- 🟢 긴 줄(>120자) 지양.

## 6장 — 객체와 자료 구조
- 🟠 도메인 객체를 게터/세터 자루로 만들지 말 것(맹목적 접근자). 동작을 노출하고 데이터를 숨겨라. (R6.1)
- 🟡 DTO/요청·응답 페이로드 = 순수 `data class`, 로직 없음(정상). 살찐 `@Entity`에 비즈니스 로직+`save/find` 누적 → 분리. (R6.9/R6.10)
- 🟠 **디미터 법칙** — `a.getB().getC().getD()` 기차 충돌 금지. ("tell, don't ask") (R6.5/R6.7) → G36
  - 주의: `?.` 체인이 기차 충돌을 가릴 수 있음(안전호출 ≠ 디미터 준수). 같은 객체 위 fluent 호출은 OK.
- 🟡 기능 욕심(Feature Envy): 남의 객체 게터를 잔뜩 끌어와 계산 → 로직을 그 객체로 이동. (G14)

## 7장 — 오류 처리 (Kotlin 널 안정성과 정렬됨)
- 🟠 오류 코드/플래그 반환 대신 예외. (R7.1)
- 🟠 **예외에 컨텍스트 제공** — 실패한 연산/타입을 담은 메시지 + 원인 체이닝(`cause`). (R7.4)
  - FLAG: `throw RuntimeException()` / `throw e`(메시지·원인 없음), 삼키는 `catch`.
- 🟡 벤더별 예외를 어댑터에서 하나의 도메인 예외로 번역. Spring은 `@ControllerAdvice` + 소수 도메인 예외. (R7.5)
- 🟠 **null 반환/전달 금지** — 던지거나, 빈 컬렉션/특수 케이스 객체/`sealed` 결과로. (R7.7/R7.8)
- 🟡 예상되는 비즈니스 분기를 `try/catch` 제어 흐름으로 쓰지 말 것 → 특수 케이스/`sealed` 결과. (R7.6)
- 🟠 `@Transactional` 롤백 의미가 try 블록 의도와 일치하는지. `Closeable`은 `use {}`.

## 8장 — 경계
> 헥사고날의 근거. 상세는 `architecture.md` 참조.
- 🔴/🟠 외부 패키지/SDK 타입(`Map`, `JsonNode`, 벤더 모델)을 공개 시그니처·여러 레이어로 흘리지 말 것 → 포트+어댑터로 격리. (R8.1~R8.3)
- 🟡 새/업그레이드 의존성엔 학습 테스트(경계 테스트)로 회귀 방지. (R8.4/R8.5)

## 9장 — 단위 테스트
- 🟠 프로덕션 코드 추가 시 테스트 없음(또는 사후 해피패스만) → 테스트 요구. (R9.1)
- 🟡 테스트도 프로덕션 품질. AAA(Given-When-Then) 구조. 가독성 최우선. (R9.2~R9.4)
- 🟡 **FIRST**: Fast(불필요한 `@SpringBootTest` 지양, 실 DB/네트워크·`Thread.sleep` 금지),
  Independent(공유 가변 상태·순서 의존 금지), Repeatable(`now()`/랜덤/타임존 → `Clock` 주입·고정 시드),
  Self-validating(`println`/수동확인 금지), Timely. (R9.8~R9.12)

## 10장 — 클래스
- 🟠 **SRP** — 변경 이유는 하나. 신/거대 서비스(`*Service`/`*Manager` 메서드 수십 개) → 책임 분리. (R10.8)
- 🟡 "if/and/or/but" 없이 ~25단어로 설명되어야. 응집도 최대화(인스턴스 변수 적게, 메서드가 그것들을 사용). (R10.7/R10.10)
- 🟠 컨트롤러에 비즈니스 로직, 서비스에 영속성+도메인+포맷팅 혼재 → 분리.
- 🟡 비공개 우선(`private val`/`internal`). "테스트 위해" 가시성 넓히기 지양.
- 🟡 **OCP/DIP** — 타입 분기로 매번 수정되는 중심 클래스 → 다형성/sealed. 구체 협력자 `new` 대신 생성자 주입. (R10.13/R10.14)

## 11장 — 시스템
> 상세는 `architecture.md`. 핵심: 구성/사용 분리, DI/IoC, 도메인 프레임워크 프리, AOP로 횡단 관심사.

## 12장 — 창발성 (단순 설계 4규칙, 우선순위 순)
1. 🟠 모든 테스트 통과(테스트 가능 설계 강제) — 커버리지 게이트(Kover/JaCoCo ~80%) on 변경 코드. (R12.1)
2. 🟡 중복 제거(DRY) — 복붙, 반복 `when(type)` → 다형성/전략/템플릿 메서드. (R12.2)
3. 🟡 의도 표현 — 정직한 이름, 작은 함수/클래스, 표준 용어, 문서로서의 테스트. (R12.3)
4. 🟢 클래스/메서드 수 최소화 — 단, 위 3개를 희생하지 말 것(과분할 금지). (R12.4)

## 13장 — 동시성 (Spring 백엔드 핵심 버그원)
- 🔴 **CRITICAL**: **싱글톤 스코프 `@Service`/`@Component` 빈에 가변 인스턴스 상태** → 요청 스레드 간 공유 데이터 레이스. (전형적 버그)
- 🔴 스레드 간 공유 `HashMap`/`mutableListOf` → `ConcurrentHashMap`/원자 연산/`Mutex`.
- 🟡 동시성 코드를 비동시성 코드와 분리(SRP). 공유 자료 최소화, 임계영역 작게. 불변 데이터 선호(`val`/`copy()`). (R13.1~R13.3)
- 🟠 하드코딩된 디스패처/스레드 수 → 주입(`CoroutineDispatcher`). 중첩 락(데드락), 종료 시 타임아웃 없는 join 주의.
- 🟢 "가끔 깨지면 그냥 재실행" 태도 금지 — 동시성 테스트 실패는 진짜 버그로 취급. (R13.10)

## 17장 — 냄새와 휴리스틱 (자주 쓰는 코드)
- **G5 중복**: 복붙·반복 `when(type)` → 다형성.
- **G23 다형성 > if/else/switch**: 타입 분기 반복 → `sealed` + `when`.
- **G25 매직 숫자 → 명명 상수**: 타임아웃·페이지 크기·코드 → `const val`/enum.
- **G26 정확하라**: 통화 `BigDecimal`(Double 금지), 미확인 nullable, "첫=유일" 가정, 누락된 `@Transactional`/락, 과도하게 넓은 선언 타입.
- **G28 조건 캡슐화**: 복잡한 `&&/||` → 명명된 술어 함수/확장 프로퍼티.
- **G30 함수는 한 가지만** / **G34 추상화 한 단계만 내려가기** / **G36 디미터(추이적 탐색 금지)**.
- **N7 이름으로 부수효과 설명**: 게터 이름인데 변경/캐시/DB 쓰기 → 이름 수정 또는 분리.
- **F4/G9 죽은 코드**: 미사용 함수/빈/엔드포인트/도달 불가 분기 → 제거.
- **T1/T5 테스트**: 해피패스만 금지, 경계 조건(빈/단일/최대/off-by-one/null) 테스트 요구.

> 결론(Clean Code): *"규칙 목록이 깨끗한 코드를 보장하지 않는다. 진짜 목표는 가치 체계다."*
> 리뷰어는 규칙을 기계적으로 적용하지 말고 트레이드오프와 맥락을 함께 설명한다.

## 리뷰 훅
- [ ] 🟡 이름이 의도를 드러내는가 (주석으로 보완 필요 없음), 매직 리터럴은 명명 상수인가.
- [ ] 🟠 함수가 한 가지만 하는가, 플래그(boolean) 인자가 없는가, 명령/조회가 분리됐는가.
- [ ] 🟠 예외에 컨텍스트+원인이 있는가, 삼키는 `catch`가 없는가, null 반환/전달이 없는가.
- [ ] 🟠 디미터 법칙 위반(기차 충돌 `a.getB().getC()`)이 없는가.
- [ ] 🔴 싱글톤 빈에 가변 인스턴스 상태가 없는가 (13장 동시성).
- [ ] 🟡 클래스가 SRP를 지키는가 (거대 서비스/매니저 없음), 중복(DRY)이 제거됐는가.
- [ ] 🟢 주석 처리된 코드/죽은 코드가 없는가.
