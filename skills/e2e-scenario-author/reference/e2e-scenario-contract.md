# E2E Scenario Contract — version 1

This bundled file is the canonical bootstrap source for `docs/e2e-scenarios/CONTRACT.md`. The author copies it
only when the project contract is absent. Once created, the project copy is reviewable application-owned input;
the author never silently overwrites it. All three E2E skills fail closed when its `contractVersion` is unsupported.

## 1. Catalog and scenario block

The catalog header is deterministic and contains no wall-clock value:

```markdown
<!-- AUTO-GENERATED by e2e-scenario-author. DO NOT EDIT. Human notes belong in docs/e2e-scenarios/notes.md. -->
<!-- Source fingerprint: sha256:<64 lowercase hex> -->
<!-- Contract: docs/e2e-scenarios/CONTRACT.md version 1 -->

# E2E Scenario Catalog
```

Every scenario starts with ``### `E2E-<TOKENS>` — <observable title>`` and contains this exact table key order:

1. `Target`
2. `Purpose`
3. `Preconditions`
4. `Dataset`
5. `Expected`
6. `Mutates`
7. `Depends-on`
8. `Captures`
9. `Notes`

Grammar-bearing scalar values may use one Markdown inline-code wrapper; consumers remove it before validation.

`Target` is source-inventory identity, not free prose. After removing inline-code wrappers and normalizing
whitespace, it is exactly one of:

- HTTP: `<METHOD> <absolute-route> (<discovered-module>)`
- Kafka: `KAFKA <resolved-topic> (<discovered-module>)`
- outbox: `OUTBOX <handler-owner> (<discovered-module>)`

Every catalog target exists in the inventory generated from the same source fingerprint. Each inventory
`required_behaviors` token has at least one scenario on that exact target whose ID ends in `-<BEHAVIOR>`.

Each scenario has exactly one primary executable fence with info string `http`, `sql`, or `shell`. A scenario whose
`Mutates` value is not `—` also has exactly one following `shell` teardown fence. The first non-blank teardown line
is `# teardown`. A read-only scenario must not have a teardown fence. The runner executes teardown with finally
semantics after primary pass, failure, or timeout; teardown failure makes the scenario fail.

## 2. Dataset

`Dataset` is `—` or comma-separated `key=value` entries. Values are synthetic literals discovered from repository
fixtures or symbolic `{{seed.TOKEN}}` references. The catalog must not contain real email addresses, phone numbers,
resident-registration numbers, credentials, production identifiers, or invented numeric fixture ranges.

Runner result JSON normalizes a parsed dataset to an object. If a legacy value cannot be parsed, it uses
`{"_raw":"<verbatim>"}` with `parsed=false`; new author output must be parseable.

## 3. Dependencies and captures

- Independent: `Depends-on: —`.
- Dependent: `Depends-on: [E2E-ID, E2E-ID]`; array brackets are mandatory for one dependency too.
- Every referenced ID exists and the graph is acyclic.
- `Captures` is `—` or comma-separated tokens matching `^[A-Z][A-Z0-9_-]*$`.
- A descendant reads an ancestor capture as `{{prev.TOKEN}}`.

## 4. Preconditions

`Preconditions` is `—` or `&&`-joined predicates:

```text
<probe-key> <operator> <literal>
```

- probe key: `^[a-z][a-z0-9_.-]*$`
- operator: `==`, `!=`, `>=`, `<=`, `>`, `<`
- literal: boolean, integer, quoted string, or `{{seed.TOKEN}}`

Examples: `service.app-api.ready == true`, `opensearch.articles.count >= 100`.

## 5. Run result JSON

The result root requires `schemaVersion`, `contractVersion`, `runId`, `startedAt`, `finishedAt`, `environment`,
`catalog`, `scope`, `summary`, and `results`. Both versions are `1`.

Each result requires `id`, `status`, `target`, `dataset`, `dependsOn`, `actual`, `expected`, `latencyMs`,
`skippedReason`, and `evidence`. `dependsOn` is always an array. Status is `PASS`, `FAIL`, `SKIPPED`,
`FAILED-DEPENDENCY`, or `PROBE-ERROR`.

- `PASS`: `actual` and `latencyMs` are present; required evidence paths are present.
- `FAIL`: `actual`, `latencyMs`, raw-body path, and failure-log path are present.
- `SKIPPED` / `FAILED-DEPENDENCY`: `actual`, `latencyMs`, and raw-body path are `null`.
- `PROBE-ERROR`: probe failure is explicit and never counted as an unmet precondition.

## 6. Mutation and teardown

`Mutates` is `—` or a comma-separated list matching `^[a-z][a-z0-9_.-]*$`. Every state-changing HTTP request,
message publication, outbox flow, or handler side effect declares at least one resource and includes the teardown
fence from section 1. Ordering a scenario last does not make it repeatable and is not a cleanup strategy.

Teardown is shell-only. SQL fences remain read-only (`SELECT` or `WITH … SELECT`). Teardown commands use the
runner allowlist, use one command per line without pipes, chains, redirections, command substitutions, or line
continuations, and must reference the declared resource or a captured identifier. A cleanup failure is preserved as
failure evidence; it is never masked by a primary PASS.

## 7. Masking

Before writing Markdown, JSON, raw bodies, logs, or HTML, mask at least:

- authorization/cookie/session tokens;
- password, secret, access-key, refresh-token fields;
- email, phone, and resident-registration-number shapes;
- project-declared sensitive IDs and values.

Masking is defense in depth: runner and renderer both apply it. A new sensitive shape requires a coordinated
contract change reviewed with all three skills.

## 8. Source inventory binding

The author generates an ephemeral canonical JSON inventory with schema
`vulpora.e2e-surface-inventory/v1` before rendering the catalog. It records the detected profile, complete
fingerprinted input paths, source fingerprint, and every discovered surface's stable key, exact target, source
location, and required behavior floor. The inventory is validation input, not a fourth project artifact.

The catalog header fingerprint must equal `source_fingerprint`. Validation fails for duplicate surfaces or targets,
catalog targets absent from the inventory, or missing required behavior coverage. A runner regenerates the same
inventory read-only. When its fingerprint matches the catalog, inventory-bound validation is mandatory before any
scenario executes; a mismatch follows the runner's explicit stale-catalog decision path.
