# 시스템 경계 입력 검증

요청 DTO는 신뢰 경계(trust boundary)의 첫 관문이다. 무엇을, 어디서, 어떻게 검증하는지 정리한다.
출처: OWASP Input Validation Cheat Sheet + Jakarta Bean Validation 3.0 Spec.

## 1. 핵심 원칙

- **외부 입력은 신뢰하지 않는다.** 클라이언트·서드파티·파일·업스트림 응답 모두 검증 대상.
- **경계에서 검증한다.** 컨트롤러(@RequestBody @Valid)에서 한 번 걸러 내부 계층의 신뢰를 확보.
- **허용 목록(allowlist) 우선.** "받을 것"을 명시하고 나머지는 거부. 블록리스트는 우회되기 쉽다.
- **빠르게 실패.** 부적합 입력은 처리 전에 `400`으로 거부(principles §4).

## 2. 무엇을 검증하나 (구조/형식)

- **존재**: 필수 필드 누락(`@NotNull`/`@NotBlank`/`@NotEmpty`).
- **타입**: 숫자/날짜/열거형 등 의미 있는 타입으로 받기(문자열 남용 금지, principles §7).
- **길이/크기**: `@Size`로 상·하한. 저장소/프로토콜 한도와 일치.
- **범위**: `@Min/@Max/@Positive/@DecimalMin` 등.
- **형식**: `@Email`, `@Pattern`(과도한 백트래킹 정규식 주의 — ReDoS).
- **멤버십**: 유한 집합은 enum으로 받아 자동 거부.

## 3. 검증 vs 정제 vs 인코딩 (구분)

- **검증(validation)**: 규칙에 맞으면 통과, 아니면 거부. 요청 DTO의 일차 책임.
- **정제(sanitization)**: 입력을 고쳐서 받아들이기. 임의 변형은 의미를 왜곡할 수 있어 신중히. OWASP는
  "검증 우선, 정제는 보조"를 권한다.
- **출력 인코딩(output encoding)**: XSS 방어는 입력 검증이 아니라 **출력 컨텍스트**에서 인코딩으로 해결한다.
  요청 DTO 검증으로 XSS를 막으려 하지 않는다(역할 분리).

## 4. 검증 vs 비즈니스 규칙 경계

- DTO 검증 = 형식/구조(상태 무관). 예: 금액 ≥ 0, 수량은 양수, 코드가 enum 멤버.
- 비즈니스 규칙 = 상태 의존. 예: "잔액 초과 금지", "중복 주문 금지". → 서비스 계층 책임(principles §9).
- 둘을 섞으면 DTO가 도메인 상태에 결합되어 재사용·테스트가 어려워진다.

## 5. 위험 입력 유형 별 주의

- **식별자**: 경로 변수로 받고 권한 검사는 서비스에서. IDOR 방지는 검증이 아닌 인가의 책임.
- **자유 텍스트**: 길이 상한 필수. 저장/표시 시 컨텍스트 인코딩.
- **파일/멀티파트**: 크기·확장자·MIME 검증, 경로 조작(path traversal) 방지.
- **숫자**: 오버플로/음수/정밀도(`@Digits`) 고려.

## 6. 실패 응답

- 검증 실패는 `400 Bad Request`. 내부 구조/스택을 노출하지 않는다.
- 표준화된 오류 본문(RFC 9457 Problem Detail) 사용 권장(에러 처리 KB 참조).

## 리뷰 훅

- [ ] 모든 외부 입력이 컨트롤러 경계에서 검증되는가(미검증 데이터가 서비스로 흐르지 않는가)?
- [ ] 허용 목록 방식으로 받을 값을 명시했는가?
- [ ] 형식 검증(DTO)과 비즈니스 규칙(서비스)이 분리되어 있는가?
- [ ] 자유 텍스트/파일 입력에 길이·크기·형식 제한이 있는가?
- [ ] XSS는 입력 검증이 아니라 출력 인코딩으로 다루는가?
- [ ] 실패 시 400으로 빠르게 실패하고 내부 정보를 노출하지 않는가?
