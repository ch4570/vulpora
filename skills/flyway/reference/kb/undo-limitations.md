# KB: Undo 한계 / 롤백 전략

> 근거: Flyway 문서(Undo migrations). Undo는 에디션·범위 제약이 있고 데이터 손실을 되돌리지 못한다.

## Undo(`U`)의 한계
- Undo 마이그레이션(`U<version>__...`)은 **수동으로 작성한 역방향 SQL**이다 — 자동 생성이 아니다.
- 데이터 손실(drop column/table)을 되돌릴 수 없다(역SQL이 데이터를 복원하지 못함).
- 일부 기능은 에디션(유료)에 묶이며, 모든 상황에서 안전한 자동 롤백을 보장하지 않는다.
- 결론: **undo에 의존한 운영 롤백을 설계하지 않는다.**

## 권장 롤백 전략
1. **순방향 복구(forward-fix)**: 잘못된 변경을 되돌리는 **새 versioned 마이그레이션**을 추가.
   (적용된 마이그레이션은 불변이므로 앞으로만 전진.)
2. **백업/복제본**: 위험 변경 전 스냅샷·PITR. 데이터 손실 변경의 유일한 진짜 안전망.
3. **확장-수축(expand–contract)**: 파괴적 변경을 비파괴 단계로 쪼개 무중단 롤백 여지 확보
   (새 컬럼 추가 → 이중 쓰기 → 백필 → 읽기 전환 → 옛 컬럼 제거).

## 리뷰 훅
- [ ] 운영 롤백을 undo가 아니라 forward-fix로 설계했는가.
- [ ] 데이터 손실 변경(drop) 전에 백업/스냅샷 계획이 있는가.
- [ ] 파괴적 변경을 expand–contract로 단계화했는가.
- [ ] undo 파일을 쓴다면 역SQL을 손으로 정확히 작성했고 한계를 인지했는가.
