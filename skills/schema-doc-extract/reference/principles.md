# 스키마 문서 추출 핵심 원칙 (Principles)

> Flyway 마이그레이션과 엔티티/ORM 코드에서 스키마를 **정적으로** 추출해 ERD + 테이블 명세를 만드는
> 판단 기준("헌법"). KB(공식 문서 distill)가 "사실·규칙"이라면 이 문서는 "통찰·판단 기준"이다.
> 충돌 시 **KB(공식 문서)가 우선**.
>
> **출처(Sources)**
> - Flyway Documentation (Red Gate) — https://documentation.red-gate.com/fd/
> - Mermaid Entity Relationship Diagram — https://mermaid.js.org/syntax/entityRelationshipDiagram.html
> - 산출물 레이아웃·명세 포맷은 Vulpora 내부 규약(KB `output-layout`).

---

## 0. 대전제: 정적 추출, 라이브 DB에 연결하지 않는다

- 입력은 **파일뿐**이다 — 마이그레이션 SQL과 엔티티/ORM 코드. 운영/개발 DB에 붙어 메타데이터를 긁지 않는다.
- 그래서 산출물은 어떤 환경에서도 재현 가능하고, 권한·네트워크에 의존하지 않는다.

## 1. 마이그레이션 = 물리 스키마의 단일 진실 (누적 리플레이)

- 물리 스키마(컬럼 타입·NULL·기본값·제약·인덱스)는 **마이그레이션이 진실**이다.
- **최신 파일 하나만** 보지 않는다. versioned 마이그레이션을 **버전 오름차순으로 누적 적용**한 결과가 현재 스키마다.
  `CREATE` 후의 `ALTER`/`DROP`/`ADD COLUMN`/제약 변경을 차례로 반영해야 실제 상태와 일치한다.

## 2. 코드 = 의도·네이밍·관계의 근거지만 drift가 있을 수 있다

- 엔티티/ORM은 논리명·설명(KDoc)·enum·연관관계의 **의도**를 준다.
- 그러나 코드는 마이그레이션과 어긋날 수 있다(미적용 필드, 이름 차이). 물리는 마이그레이션이 이기고, **불일치는 drift로 표기**한다.

## 3. 절대 지어내지 않는다 (never invent)

- 마이그레이션·코드에 근거가 없는 컬럼·타입·관계를 **추측해 채우지 않는다.**
- 불확실하면 명세에 "근거 부족"으로 남기거나 drift로 보고한다. 빈칸을 그럴듯한 값으로 메우지 않는다.

## 4. 결정적·멱등 산출 (diff 가능)

- 같은 입력이면 **항상 동일한 파일**을 만든다. 재실행이 무의미한 diff를 만들지 않게 한다.
- 정렬을 고정한다: 테이블은 **스키마명 → 테이블명 알파벳순**, 컬럼은 마이그레이션 선언 순서.

## 5. 관계는 FK 근거가 있을 때만, 카디널리티는 NULL 여부로

- ERD 관계선은 SQL `FOREIGN KEY`/`REFERENCES` 또는 명시적 ORM 연관(`@ManyToOne`/조인 컬럼) **근거가 있을 때만** 그린다.
- 카디널리티: FK 컬럼이 NOT NULL이면 1, NULL 허용이면 0..1. 추정 관계는 그리지 않는다.

## 6. ERD는 모든 테이블을 포함한다

- 관계가 없는 고립 테이블도 ERD 엔티티로 **반드시** 표시한다(누락 = 불완전한 지도).
- 테이블 명세도 마이그레이션의 모든 테이블을 1:1로 다룬다.

## 7. 실데이터 값은 마스킹/생략 (PII 안전)

- 추출 대상은 **스키마(구조)** 다. 시드/샘플 행의 **실제 값을 산출물에 넣지 않는다.**
- 예시가 필요하면 일반 placeholder(`<email>`, `<id>`)를 쓴다. PII·비밀이 문서로 새지 않게 한다.

## 8. 사람이 읽고 diff 하는 산출물

- ERD는 렌더 가능한 Mermaid, 명세는 안정된 컬럼 순서의 Markdown 표. 리뷰어가 변경분을 git diff로 읽을 수 있어야 한다.
- 포맷·헤더·섹션 순서를 고정해 노이즈 diff를 막는다.
