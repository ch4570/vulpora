# KB: 테스트 피라미드

## 핵심 명제 (Fowler *TestPyramid*)
- 피라미드는 **테스트 종류별 상대 개수(비율)** 에 관한 비유다: 아래로 갈수록 많고 빠르고,
  위로 갈수록 적고 느리고 비싸다.
- 권고 형태: **단위(아래) ≫ 통합/서비스(중간) ≫ E2E/UI(위).** Google이 자주 인용하는
  경험칙은 70% / 20% / 10% 이지만, 절대값보다 **"위로 갈수록 적게"** 라는 형태가 본질이다.
- Fowler의 두 가지 보정 포인트:
  1. **계층 이름에 집착하지 마라.** 중요한 건 "얼마나 빠른가"와 "실패 시 원인을 얼마나
     좁게 짚는가"이다.
  2. **위 계층 테스트가 잡는 버그는 가능한 한 아래 계층으로 밀어내라(push down).**

## 각 층의 비용·신뢰도 트레이드오프
| 계층 | 속도 | 실패 시 원인 지목 | 깨지기 쉬움(플레이키) | 외부 의존 | 적정 개수 |
|------|------|------------------|----------------------|-----------|-----------|
| **단위(Unit)** | 매우 빠름(ms) | 좁고 정확 | 낮음 | 없음(주입) | 가장 많이 |
| **통합(Integration/Service)** | 중간 | 중간 | 중간 | DB/슬라이스 등 일부 | 중간 |
| **E2E/UI** | 느림(s~m) | 넓고 모호 | 높음 | 전체 스택 | 가장 적게 |

- **위로 갈수록 비싼 이유:** ① 부팅·네트워크·렌더링으로 느리고 ② 실패가 "어딘가에서 났다"는
  넓은 신호만 주며 ③ 타이밍·환경 의존으로 플레이키하다.
- **신뢰도 역설:** E2E는 "실제에 가깝다"는 신뢰를 주지만, 느리고 불안정해서 자주 무시되면
  오히려 신뢰가 낮아진다.

## 안티패턴: 아이스크림 콘 (Inverted Pyramid)
- E2E·수동 테스트가 비대하고 단위가 빈약한 형태. 피드백이 느리고, 작은 변경에도 광범위한
  E2E가 깨져 유지보수 비용이 폭증한다.
- Google Testing Blog(*Just Say No to More End-to-End Tests*): E2E는 느리고 불안정하며
  실패 원인 분석이 어렵다 → **E2E를 늘리지 말고 하위 계층으로 커버리지를 옮겨라.**
- 또 다른 안티패턴 **모래시계(Hourglass):** 단위와 E2E는 많은데 중간(통합)이 비어 있어,
  계층 간 연결 결함을 E2E에서야 비싸게 발견한다.

## 이 스킬에서의 적용 (`SKILL.md` 연계)
- 아래 base class를 제공하는 저장소 프로필에서는 선택이 곧 계층 선택이다:
  `AbstractTest`/`AbstractMockTest`(단위) →
  `AbstractDataBaseTest`/`AbstractWebMvcTest`(통합 슬라이스) → 전체 부팅(E2E).
- **가장 가벼운 base를 고르는 `TST-2`** 가 곧 "버그를 가장 낮은 계층으로 밀어내라"의 구현이다.

## 리뷰 훅
- [ ] 이 동작을 **더 낮고 빠른 계층**에서 검증할 수 있는데 굳이 E2E/통합으로 올리지 않았는가.
- [ ] E2E/broad 테스트 개수가 단위 대비 비정상적으로 많지 않은가(아이스크림 콘 징후).
- [ ] 중간(통합) 계층이 비어 계층 간 결함이 E2E로만 드러나는 구조(모래시계)는 아닌가.
- [ ] 느린 상위 테스트가 실패할 때 **원인을 좁게 짚어주는** 하위 테스트가 함께 존재하는가.
- [ ] 무거운 base class(`AbstractDataBaseTest`/`AbstractWebMvcTest`)를 실제 필요 없이 쓰지 않았는가(`TST-2`).
