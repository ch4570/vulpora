# PostgreSQL 스키마 설계 — 핵심 원칙 (Principles)

> 이 문서는 데이터 모델링·물리 설계의 판단 기준을 담은 "헌법"이다. KB가 "제약 규칙·구문"이라면
> 여기는 "무엇을 우선하고 어디서 타협할지"의 판단 기준이다. **충돌 시 KB(공식 문서)가 우선**.
>
> **출처(Sources)**
> - 유동오, 『핵심 데이터 모델링』(디비안) — ER 이론, 정규화, 개념/논리/물리 모델링, 무결성, 이력
> - PostgreSQL 공식 문서: `Data Definition`, `Constraints`, `Data Types`, `Range Types`,
>   `Lexical Structure(Identifiers)` (docs/current)
>
> 책은 Oracle 기준이 많으므로 물리 구현은 PostgreSQL로 치환한다(시퀀스→`IDENTITY`,
> 기간 중첩 금지→`EXCLUDE USING gist`, `NVL`→`COALESCE` 등).

## 0. "쉬운 80점" 설계가 "어려운 100점"을 이긴다 — 단, 무결성은 예외
- 이상적 설계보다 **현실에 적용 가능한 설계**를 우선한다. 그러나 "쉬움"이 무결성·정합성을
  포기하는 핑계가 되어선 안 된다. 무결성은 타협 불가 영역이다.

## 1. 무결성은 DB에 건다 — 애플리케이션만 믿지 않는다
- **모든 테이블에 PK.** **NOT NULL을 기본값**으로(선택적일 때만 NULL).
- **FK로 참조무결성**을 걸고 `ON DELETE`를 의미에 맞게(CASCADE/RESTRICT/SET NULL).
- **FK 컬럼엔 인덱스를 직접** 만든다(PG는 자동 생성 안 함 → 부모 변경 시 자식 풀스캔/락 확대).
- **자연키엔 UNIQUE**(인조 PK가 있어도 업무 유일성 보장). 도메인 규칙은 CHECK, 교차행 규칙은
  UNIQUE/EXCLUDE/FK.

## 2. 정규화가 기본, 반정규화는 근거를 남긴 예외
- 정규화는 이상현상을 제거한다. 반정규화는 **성능 근거 + 정합성 유지책(트리거/앱/배치) +
  문서화**가 함께일 때만. 다대다는 교차 엔티티로 해소한다.

## 3. 모델은 6대 질적 특성으로 자평한다
- **완전성·정확성·비중복성·명확성·유연성·가독성.** 같은 사실은 한 번만 표현하고, 불가피한
  중복/파생은 반드시 문서화한다.

## 4. 식별자는 자연키 우선, 인조키는 기준이 있을 때
- 자연키가 안정·단순·유일하면 그대로 PK. **복합키가 너무 길거나, 값이 변하거나, 외부 노출이
  곤란**하면 인조키(`bigint GENERATED ALWAYS AS IDENTITY`). 외부 노출/분산은 UUID(시간순 v7 권장).

## 5. 일반화/통합은 유연성과 무결성의 트레이드오프다
- 통합은 배타관계를 해소해 개발생산성·유연성을 높이지만 **NOT NULL/FK 제약이 곤란**해진다.
  물리 구현(단일 테이블 / 분리 + 슈퍼 FK / 서브타입별 테이블)을 의식적으로 고르고 근거를 남긴다.

## 6. 타입은 의미대로 고른다 (PG 권장)
- 금액·정밀계산은 `numeric`(부동소수점 금지), 식별자는 `bigint`/`IDENTITY`, 시각은
  `timestamptz`(권장), 날짜만 `date`. 반정형은 `jsonb`(+GIN)이되 **정규화 회피용 남용 금지**.
  파생값은 `GENERATED ALWAYS AS (...) STORED`.

## 7. 이력은 조회 패턴으로 선택하고 중첩을 DB가 막게 한다
- "특정 시점 상태"를 자주 묻는다면 선분 이력. **같은 키의 기간 중첩 금지**는 `EXCLUDE USING
  gist (key WITH =, period WITH &&)` + range 타입으로 DB가 보장한다(PG의 강력한 무기).

## 8. 명명·표준화를 일관되게
- 식별자는 전부 `snake_case` 소문자(큰따옴표 대소문자 혼용 금지). 같은 의미는 같은 이름·타입
  (표준 단어/도메인/용어). 의미 없는 이름·다목적 컬럼을 피한다.
