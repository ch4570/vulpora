# 데이터 모델링 (Data Modeling)

> 출처: 『핵심 데이터 모델링』(유동오) 1~3·5장(벤더 무관 ER 이론) + PostgreSQL `Data Definition`(물리 구현 검증).

## 1. ER 모델의 6대 질적 특성 (모델 자가검증 체크리스트)

설계/리뷰 시 이 6개로 모델을 평가한다.

1. **완전성(Completeness)** — 모든 요구사항이 모델에 표현되었는가. (예: 상품 단가가 변하면
   주문 시점 단가/금액을 같이 저장해야 함)
2. **정확성(Correctness)** — ER 개념을 올바르게 사용했는가. 엔티티 대신 속성을 쓰지 않았는가,
   관계 대신 엔티티를 쓰지 않았는가, 식별자/카디널리티/옵셔널리티가 명확한가.
3. **비중복성(Non-redundancy)** — 같은 사실이 한 번만 표현되는가. (부서의 "직원 수"는 직원에서
   집계 가능 → 저장 불필요). 불가피한 파생/중복은 **반드시 문서화**.
4. **명확성/단순성** — 추가 설명 없이 의미가 통하는가. (`주소1/주소2` < `기본주소/상세주소`)
5. **유연성(Flexibility)** — 업무 확장을 흡수하는가. 대표 기법은 **일반화/통합**(고객유형 추가로
   개인·법인·단체 확장).
6. **가독성** — 위→아래, 좌→우, 부모를 자식 위에, 관계선 교차 최소화, 중요 속성 위쪽.

## 2. 엔티티/관계/속성

- **엔티티**: 둘 이상의 인스턴스가 존재할 수 있고, 둘 이상의 속성을 가지며, 인스턴스를 식별할
  식별자가 하나 이상 있어야 한다.
- **엔티티 분류(식별 도구로만 활용)**: 핵심(Key, 부모 없는 독립: 고객·상품·조직) / 중요(Main,
  핵심 간 거래로 생성: 계약·주문) / 행위(Action, 지속 발생: 청구내역). 강한/약한, 독립/교차도 참고.
- **약한 엔티티 / 종속 엔티티**: 다른 엔티티의 식별자를 상속(예: 주문상품 = 주문번호 상속).
- **교차 엔티티**: 다대다(M:N) 관계 해소용. 논리 모델링에서 도출.

## 3. 정규화 (기본값)

- 정규화는 이상현상(삽입/갱신/삭제 이상)을 제거한다. **기본은 정규화.**
- 1NF: 반복 그룹 제거(상품1·상품2·상품3… → 주문상품 엔티티로 분리).
- 2NF: 부분 함수 종속 제거(복합키 일부에만 종속되는 속성 분리).
- 3NF: 이행 종속 제거(키가 아닌 속성에 종속되는 속성 분리).
- **반정규화는 예외.** 적용하려면:
  1) 성능 근거(실측/패턴)가 명확하고, 2) **정합성 유지 책임**(트리거/애플리케이션 규칙/배치)을
  함께 설계하고, 3) **문서화**한다.

## 4. 일반화/특수화, 슈퍼타입/서브타입

- **일반화(통합, 상향식)**: 개인고객+법인고객 → 고객. 동일 업무처리 대상/동일 관점 분석이면 통합.
  - 장점: 배타관계 해소 → `UNION`/Outer Join 감소, 개발생산성·성능·유연성↑.
  - 단점: 속성 의미 모호, **NOT NULL/FK 제약을 못 거는 무결성 약화** → 애플리케이션/CHECK로 보강.
- **특수화(하향식)**: 고객 → 개인/법인. 서브타입별 고유 속성을 분리해 업무 규칙을 정확히 반영.
- **PostgreSQL 물리 구현 선택지**:
  1. **단일 테이블(Single Table)** + 타입 컬럼 + 부분 CHECK/부분 인덱스 (통합, 조회 단순)
  2. **테이블 분리(Class Table)** + 공통 슈퍼 테이블 FK (무결성 강함, 조인 필요)
  3. 서브타입별 독립 테이블 (서브타입 간 공통 조회 적을 때)
  - 트레이드오프를 의식적으로 선택하고 근거를 남긴다.

## 5. 식별자 전략 (인조 식별자는 언제?)

- **자연키 우선**: 안정적(값이 안 변함)·단순·유일하면 자연키를 PK로.
- **인조(surrogate) 식별자 도입 기준**:
  - 복합 자연키가 너무 길거나(조인·인덱스 비용),
  - 자연키 값이 변할 수 있거나(주민번호 갱신 등),
  - 자연키를 외부에 노출하기 곤란할 때.
- **인조키를 써도 자연키엔 UNIQUE를 건다.** (책의 단골 경고: 인조키만 믿으면 업무적으로 같은
  데이터가 중복 입력된다.)
- PostgreSQL: `bigint GENERATED ALWAYS AS IDENTITY`(권장). 외부 노출/분산 생성은 UUID
  (시간순 v7 권장; 랜덤 UUID는 B-tree 지역성 나빠 인덱스 비대).

## 6. 5장 "모델링 이야기"의 실전 주제 (PG 관점 요약)

- **고객의 정의 / 통합 범위**: 어디까지 일반화할지는 업무·확장성·무결성의 균형. "원칙과 현실 사이".
- **공통코드 설계**: 코드그룹+코드(+FK). 만능 단일 코드테이블의 과도한 통합 경계.
- **개인정보/암호화**: 민감정보는 컬럼/테이블 분리 + 암호화. 검색 필요 시 해시 컬럼 + 부분 인덱스.
- **주소 관리**: 주소코드 표준 + 상세주소 분리.
- **이력 관리**: 점 이력 vs 선분 이력 → `history-modeling.md`.
- **순환관계**: 자기참조(상위부서코드). FK self-reference + 재귀 CTE 조회.
- **참조무결성**: FK로 DB에서 강제(가능한 한). 통합으로 FK가 곤란해지면 보강 규칙 명시.

## 리뷰 훅

- [ ] 6대 질적 특성(완전성·정확성·비중복성·명확성·유연성·가독성)으로 모델을 자평했는가.
- [ ] 정규화가 기본인가. 반정규화는 성능 근거 + 정합성 유지책 + 문서화가 함께인가.
- [ ] 다대다(M:N)를 교차 엔티티로 해소했는가.
- [ ] 일반화/통합 시 무결성 약화(NOT NULL/FK 곤란) 트레이드오프를 인지·보강했는가.
- [ ] 자연키가 불안정/길/노출 곤란일 때만 인조키를 도입했는가(자연키엔 UNIQUE 유지).
- [ ] 같은 사실이 두 곳에 중복 저장되지 않는가(중복이면 동기화 책임 명시).
