# KB: 행위 패턴 (Behavioral)

> 행위 패턴은 **객체 간 책임 분배와 상호작용(알고리즘·통신)** 을 다룬다. "분기가 흩어지고
> 행동이 변한다"는 신호에서 가장 먼저 검토한다.

## 패턴 요약표 (전체)

| 패턴 | 의도(1줄) | 적용 신호 | 오용/과설계 신호 |
|------|-----------|-----------|------------------|
| **Strategy** | 교체 가능한 알고리즘군을 캡슐화 | 정책/계산 분기가 흩어지고 교체 잦음 | 변형 1개뿐, `when`이면 충분 |
| **Template Method** | 골격 고정 + 일부 단계만 서브클래스 | 절차 골격 중복, 일부 스텝만 다름 | 단계가 사실상 안 변함 |
| **Observer** | 상태 변화를 구독자에게 발행 | 한 변화에 다수 반응, 구독자 가변 | 수신자 1개·동기 호출로 족함 |
| **State** | 상태별 행동을 상태 객체로 분리 | 동작이 상태에 따라 크게 갈리고 전이가 if로 엉킴 | 상태 2개·전이 단순 |
| **Command** | 요청을 객체로 캡슐화 | 실행취소/큐잉/로깅/트랜잭션 필요 | 단순 메서드 호출로 충분 |
| **Chain of Responsibility** | 처리자를 사슬로 연결 | 처리자 후보가 여럿·동적, 통과 규칙 다양 | 처리자 고정·단일 |
| **Iterator** | 내부 표현 노출 없이 순회 | 자료구조 순회 추상화 필요 | 언어 내장 순회로 충분 |
| **Mediator** | 객체 간 통신을 중재자로 집중 | 다대다 결합이 거미줄이 됨 | 결합이 단순함 |
| **Visitor** | 구조는 두고 연산을 외부로 분리 | **안정적** 계층에 연산이 자주 추가됨 | 계층이 자주 바뀜(아래 경고) |

---

## Strategy (가장 흔히 쓰임)
- **의도**: 알고리즘군을 각각 캡슐화하고 **런타임에 교체** 가능하게 만든다.
- **적용 신호**: 할인/요금/정렬 정책처럼 분기(`when`)가 코드 곳곳에 흩어지고, 교체·추가가 잦다.
- **오용 신호**: 변형이 하나뿐이거나 거의 안 변하는데 전략 인터페이스+구현체를 만든다(YAGNI).

```kotlin
fun interface DiscountPolicy { fun apply(order: Order): Money }
class OrderService(private val policy: DiscountPolicy) {     // 주입(=DI)
    fun checkout(order: Order): Money = policy.apply(order)
}
```
> Strategy는 **Spring 생성자 주입**으로 가장 자연스럽게 실현된다(`di-strategy-factory-spring.md`).

## Template Method
- **의도**: 알고리즘 **골격은 상위에서 고정**하고, 일부 단계만 하위에서 재정의.
- **적용 신호**: 여러 클래스가 동일 절차를 반복하고 한두 스텝만 다르다(절차 중복).
- **오용 신호**: 재정의될 스텝이 사실상 없음(상속만 강요). 합성 기반 콜백/람다(전략)가 더 유연.
- Strategy(합성)와 자주 비교: 변형이 *단계 단위* 면 Template Method, *알고리즘 전체* 면 Strategy.

## Observer
- **의도**: 한 객체 상태가 바뀌면 의존 객체들에게 **자동 통지**(발행/구독).
- **적용 신호**: 도메인 이벤트(주문 완료 등)에 여러 후속 동작이 붙고 구독자가 늘었다 줄었다 함.
- **오용 신호**: 수신자가 하나뿐이면 직접 호출이 명확. 통지 순서/예외 전파 정책을 반드시 정의.
- Spring `ApplicationEvent`/`@EventListener`가 대표 실현.

## State
- **의도**: 객체의 **내부 상태에 따라 행동이 달라지도록** 상태를 객체로 캡슐화.
- **적용 신호**: `if (status == ...)` 분기가 여러 메서드에 반복되고 상태 전이 규칙이 복잡.
- **오용 신호**: 상태가 2개이고 전이가 단순하면 `enum`/`sealed` + `when`이 더 읽기 쉽다.
- Strategy와 구조는 닮았으나 **의도가 다름**: State는 전이를 알고, Strategy는 외부가 교체.

## Command
- **의도**: 요청을 **객체로 캡슐화**해 매개변수화·큐잉·로깅·실행취소(undo)를 가능케 함.
- **적용 신호**: undo/redo, 작업 큐, 트랜잭션 단위 재실행, 매크로가 필요.
- **오용 신호**: 단순 호출에 Command 래퍼만 씌움(부가 가치 없음).

## Chain of Responsibility
- **의도**: 요청을 처리할 수 있는 핸들러들을 **사슬로 연결**, 처리될 때까지 전달.
- **적용 신호**: 검증/필터/인터셉터처럼 처리자 후보가 여럿이고 동적으로 조합된다(서블릿 필터).
- **오용 신호**: 처리자가 하나로 고정이면 직접 호출.

## Iterator / Mediator / Visitor (요지)
- **Iterator**: 컬렉션 내부 표현을 숨기고 순회. Kotlin/Java는 `Iterable`/`Iterator`가 내장 →
  **대부분 직접 구현 불필요**. 커스텀 자료구조에 한해 구현.
- **Mediator**: 객체 간 다대다 결합이 거미줄이 될 때 통신을 중재자로 모아 결합을 별 모양으로.
  과하면 중재자가 신(God) 객체가 되므로 경계.
- **Visitor**: 객체 구조는 그대로 두고 **연산만 외부 클래스로 분리**. 새 연산 추가는 쉽지만
  **새 요소(타입) 추가는 모든 Visitor를 고쳐야 함**. → **계층이 안정적일 때만** 가치 있음.
  계층이 자주 바뀌면 Kotlin `sealed` + `when`이 훨씬 단순·안전(상세: `pattern-misuse-signals.md`).

## 리뷰 훅
- [ ] 흩어진 정책/계산 분기가 **둘 이상의 실재 변형**을 가질 때만 Strategy로 뽑는가.
- [ ] Template Method 도입 시 재정의될 단계가 실제로 존재하는가(아니면 합성/람다).
- [ ] Observer의 **통지 순서·예외 전파·동기/비동기** 정책이 정의됐는가, 수신자가 둘 이상인가.
- [ ] State 도입 전, 상태/전이가 `enum`+`when`으로 끝나지 않는가.
- [ ] Command가 undo/큐/로깅 같은 **실제 부가 책임**을 동반하는가.
- [ ] Chain의 처리자 후보가 실제로 여럿·동적인가.
- [ ] Visitor를 쓰는 **계층이 안정적**인가(자주 바뀌면 `sealed when`).
- [ ] Iterator/Mediator를 언어 내장/단순 호출로 대체 못 하는 명확한 이유가 있는가.
