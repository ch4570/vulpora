# KB: 구조 패턴 (Structural)

> 구조 패턴은 **클래스/객체를 더 큰 구조로 조립**하면서 구조를 유연·효율적으로 유지하는 법을
> 다룬다. 대부분 합성과 인터페이스 정렬로 결합을 낮춘다.

## 패턴 요약표

| 패턴 | 의도(1줄) | 적용 신호 | 오용/과설계 신호 |
|------|-----------|-----------|------------------|
| **Adapter** | 호환 안 되는 인터페이스를 변환 | 외부/레거시 API의 시그니처가 우리 추상과 불일치 | 직접 수정 가능한데 어댑터 추가 |
| **Bridge** | 추상과 구현을 분리해 독립 확장 | 두 변형축(추상×플랫폼)이 곱집합으로 증가 | 변형축이 하나뿐 |
| **Composite** | 부분-전체를 동일 인터페이스로 | 트리 구조를 단일/복합 구분 없이 다루고 싶다 | 계층이 없는 평면 데이터 |
| **Decorator** | 동적으로 책임 추가(합성) | 기능 조합이 폭발, 상속 서브클래스 폭증 | 조합이 고정적/소수 |
| **Facade** | 복잡 서브시스템에 단순 진입점 | 클라이언트가 다단계 호출 절차에 결합 | 호출이 이미 단순 |
| **Flyweight** | 공유로 다수 객체 메모리 절감 | 동일 불변 상태를 가진 객체가 대량 | 객체 수가 적음(조기 최적화) |
| **Proxy** | 대상 접근을 대리(지연/캐시/보호) | 지연 로딩·접근제어·캐싱·원격 대리 필요 | 부가책임이 없는데 래퍼만 추가 |

## Adapter
- **의도**: 한 클래스의 인터페이스를 클라이언트가 기대하는 다른 인터페이스로 변환.
- **적용 신호**: 외부 라이브러리/레거시의 메서드 시그니처가 우리 포트(인터페이스)와 안 맞아
  변환 코드가 호출부에 산재한다 → 어댑터로 격리(헥사고날의 어댑터와 동일 개념).
- **오용 신호**: 우리 코드라 직접 고칠 수 있는데 어댑터 층만 늘림.

```kotlin
interface NotificationPort { fun send(member: Member, text: String) }
class ExternalSmsAdapter(private val sdk: VendorSmsClient) : NotificationPort {
    override fun send(member: Member, text: String) =
        sdk.dispatch(member.phone, body = text)   // 시그니처 변환
}
```

## Bridge
- **의도**: 추상(상위 개념)과 구현(하위 메커니즘)을 **별도 계층**으로 분리해 둘을 독립 확장.
- **적용 신호**: `(도형 종류) × (렌더 방식)`처럼 변형이 두 축이고, 상속으로 곱집합 클래스가
  폭발한다 → 한 축을 합성으로 위임.
- **오용 신호**: 변형축이 하나면 단순 상속/전략으로 충분(Bridge는 과설계).

## Composite
- **의도**: 개별 객체와 객체 묶음을 **동일 인터페이스**로 다뤄 트리를 재귀적으로 처리.
- **적용 신호**: 메뉴/조직도/주문 구성처럼 leaf와 group을 구분 없이 순회·집계.
- **오용 신호**: 실제 계층 구조가 없는데 Composite로 억지 추상화.

## Decorator
- **의도**: 상속 없이 **객체를 감싸 동적으로 책임을 추가**(투명하게 같은 인터페이스 유지).
- **적용 신호**: 기능 조합(로깅+캐시+압축…)이 곱집합으로 늘어 서브클래스가 폭발.
- **오용 신호**: 조합이 소수·고정이면 데코레이터의 래핑 체인이 가독성만 해친다.

```kotlin
interface PriceCalc { fun calc(order: Order): Money }
class LoggingPrice(private val inner: PriceCalc) : PriceCalc {
    override fun calc(order: Order) = inner.calc(order).also { log(it) }
}
```

## Facade
- **의도**: 복잡한 서브시스템 묶음에 대해 **단순한 상위 인터페이스** 하나를 제공.
- **적용 신호**: 클라이언트가 서브시스템의 호출 순서/세부에 강하게 결합되어 있다.
- **오용 신호**: 단순 위임만 하는 facade(부가 가치 없이 한 겹 더 감싸기).

## Flyweight
- **의도**: 공통 **불변 상태(intrinsic)** 를 공유해 대량 객체의 메모리 사용을 줄임.
- **적용 신호**: 동일 속성 객체가 수십만 개 생성되어 메모리가 병목(가변 상태는 외부 추출).
- **오용 신호**: 객체 수가 적은데 도입(전형적 조기 최적화 — 측정 후 적용).

## Proxy
- **의도**: 실제 객체에 대한 **대리자**를 두어 접근을 제어(지연 로딩, 캐싱, 보호, 원격).
- **적용 신호**: 무거운 객체의 지연 초기화, 접근 권한 검사, 결과 캐싱, 원격 호출 래핑.
- **오용 신호**: 아무 부가 책임 없이 프록시 껍데기만 추가.
- Spring AOP의 트랜잭션/보안 프록시가 이 패턴의 대표 실현이다.

## 리뷰 훅
- [ ] 인터페이스 불일치 변환 코드가 호출부에 산재 → Adapter로 격리했는가(우리 코드면 직접 수정 검토).
- [ ] 변형축이 **둘 이상**일 때만 Bridge를 쓰는가(하나면 전략/상속).
- [ ] Composite를 쓸 만큼 실제 트리/재귀 구조가 있는가.
- [ ] Decorator 도입 전, 조합이 정말 폭발하는가(소수면 단순 상속/래퍼).
- [ ] Facade가 단순 위임을 넘어 **복잡도 은닉** 가치를 주는가.
- [ ] Flyweight/Proxy를 **측정 근거** 없이 조기 도입하지 않는가.
- [ ] Proxy가 지연/캐시/보호 등 실제 부가책임을 가지는가.
