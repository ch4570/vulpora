# 번역투 패턴

아래 표현은 금칙어가 아니다. 더 짧고 정확한 문장이 있을 때 습관적으로 쓰지 않는다는 뜻이다.

| 패턴 | 왜 어색한가 | 나쁜 예 | 좋은 예 | 써도 되는 경우 |
|---|---|---|---|---|
| `해당` | 대상을 다시 가리킬 필요가 없는데 공문서식 지시어를 붙인다. | 해당 API는 사용자 정보를 반환합니다. | 이 API는 사용자 정보를 반환한다. | 같은 문단에 후보가 여럿이고 대상을 분명히 구분해야 할 때 |
| `~에 대한` | 명사끼리 느슨하게 연결해 관계가 흐려진다. | 캐시 만료에 대한 처리를 추가한다. | 캐시가 만료되면 다시 조회한다. | `요청에 대한 응답`처럼 관계 자체가 핵심일 때 |
| `~를 통해` | 수단을 앞세워 동작이 늦게 나온다. | 이 API를 통해 주문을 조회한다. | 이 API로 주문을 조회한다. | 여러 단계의 경로나 매개체를 강조해야 할 때 |
| `진행` | 실제 동작을 숨기는 만능 명사가 된다. | 배포를 진행한다. | 배포한다. | 진행률이나 절차의 진행 상태를 말할 때 |
| `수행` | 구체적인 동사를 명사화해 문장이 무거워진다. | 입력값 검증을 수행한다. | 입력값을 검증한다. | 여러 하위 작업을 묶은 공식 작업명을 가리킬 때 |
| `~을 기반으로` | 영어 `based on`을 그대로 옮겨 관계가 모호하다. | 토큰을 기반으로 사용자를 식별한다. | 토큰에서 사용자 ID를 읽는다. | 모델·정책·표준이 실제 판단 근거일 때 |
| `~할 수 있도록` | 목적 표현이 겹치고 주동작이 뒤로 밀린다. | 재시도할 수 있도록 설정을 추가한다. | 재시도 설정을 추가한다. | 사용자 능력이나 접근성 보장이 핵심일 때 |
| `~하는 것이 가능` | 가능 여부를 명사절로 돌려 말한다. | 설정으로 timeout을 변경하는 것이 가능하다. | 설정에서 timeout을 바꿀 수 있다. | 가능성과 불가능성을 대조하는 공식 계약 문구일 때 |
| `~가 발생하는 경우` | 조건문을 길게 만든다. | 오류가 발생하는 경우 rollback한다. | 오류가 나면 rollback한다. | 법적·정책적 조건을 엄밀하게 나열할 때 |
| `~하게 됩니다` | 자연 법칙처럼 결과를 흐리고 책임 주체를 감춘다. | 요청은 worker에서 처리하게 됩니다. | worker가 요청을 처리한다. | 단계별 안내에서 실제 상태 변화를 설명할 때도 대개 직접형이 낫다. |
| 과도한 피동형 | 누가 무엇을 하는지 사라진다. | payload가 middleware에 의해 검증된다. | middleware가 payload를 검증한다. | 행위자보다 결과 상태가 중요하거나 행위자를 알 수 없을 때 |
| 불필요한 명사화 | 동작이 여러 명사 뒤에 숨는다. | 데이터 정합성 보장을 위한 검증 처리를 수행한다. | 저장 전에 값을 검증해 정합성을 지킨다. | 고정된 기능명·메뉴명·지표명일 때 |
| 영어식 긴 수식어 | 수식 대상이 늦게 나와 다시 읽게 된다. | 운영 환경에서 간헐적으로만 재현되는 연결 종료 문제 | 연결이 간헐적으로 끊긴다. 운영 환경에서만 재현된다. | 고유한 타입이나 이미 합의된 짧은 명칭일 때 |
| 같은 어미 반복 | 문장이 기계적으로 들리고 정보의 관계가 평평해진다. | 값을 읽습니다. 검증합니다. 저장합니다. 응답합니다. | 값을 읽어 검증한 뒤 저장하고 응답합니다. | 절차 목록에서 각 단계의 형식을 맞춰야 할 때 |

## 교정 순서

1. 문장에서 실제 주체와 동작을 찾는다.
2. `진행`, `수행`, `처리`를 구체적인 동사로 바꾼다.
3. 조건은 `~하면`, 원인은 `~해서`, 수단은 `~로`처럼 짧게 연결한다.
4. 한 문장에 원인·동작·결과가 너무 많으면 둘로 나눈다.
5. 바꾼 뒤 의미, 조건과 책임 주체가 원문과 같은지 확인한다.

짧게 바꾸면서 조건을 지우면 실패다. 예를 들어 `timeout이면 멱등한 요청만 재시도한다`를
`timeout이면 재시도한다`로 줄이지 않는다.
