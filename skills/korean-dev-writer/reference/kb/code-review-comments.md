# 코드 리뷰 코멘트

리뷰는 사람을 평가하지 않고 코드가 만드는 결과를 설명한다. 부드럽게 돌려 말하다가 문제를 숨기지
말고, 공격적인 단정으로 작성자를 방어적으로 만들지도 않는다.

## 기본 구조

1. 어떤 입력이나 상태에서 문제가 생기는지
2. 사용자·데이터·운영에 미치는 영향
3. 가능한 수정 방향
4. 필요하면 검증 방법

나쁨:

> 이 코드는 잘못 작성된 것 같습니다.

좋음:

> 여기서 `null`이 들어오면 예외가 발생합니다. 호출 전에 검증하거나 이 함수 안에서 처리하는 편이
> 안전합니다.

## 강도 조절

- correctness, 보안, 데이터 유실, API 계약 위반은 명확히 blocker라고 말한다.
- 유지보수 제안은 사실과 취향을 구분한다. `반드시` 대신 얻는 이점을 설명한다.
- 질문 형태를 책임 회피에 쓰지 않는다. 확정된 결함을 `혹시 문제가 되지 않을까요?`로 흐리지 않는다.
- 근거가 부족하면 단정하지 말고 확인할 조건을 묻는다.

## 표현 예

- `이 분기는 timeout도 성공으로 기록해 장애를 숨깁니다. 실패 상태를 보존하고 retry 여부를 따로 결정해야 합니다.`
- `현재 이름만으로는 초 단위인지 밀리초 단위인지 알기 어렵습니다. 단위를 이름에 넣으면 호출부의 오해를 줄일 수 있습니다.`
- `이 추상화는 구현이 하나라서 지금은 간접 호출만 늘립니다. 두 번째 변경 축이 생길 때 분리해도 늦지 않습니다.`

칭찬 코멘트도 막연한 `깔끔합니다`보다 어떤 결정이 읽기나 안전성을 높였는지 말한다.
