# 기술 설명

## 기본 순서

1. 결론이나 핵심 동작
2. 그 이유
3. 판단에 필요한 구현 세부 사항
4. 주의할 edge case와 미검증 항목

질문을 칭찬하거나 주제를 소개하는 문장으로 시작하지 않는다. `좋은 질문입니다`, `먼저 살펴보겠습니다`,
`여러 측면에서 볼 수 있습니다`를 지우고 사용자가 물은 내용부터 답한다.

## 코드 동작 설명

- 함수 호출 순서를 모두 읽어 주지 말고 데이터나 상태가 어디서 바뀌는지 설명한다.
- 분기마다 결과가 다르면 입력 조건과 관찰 가능한 결과를 짝지어 쓴다.
- transaction, thread, process, retry 경계는 실제 경계를 명시한다.
- 확인한 사실과 추론을 분리한다. 실행하지 않은 결과를 통과했다고 쓰지 않는다.

예:

> 주문 저장과 이벤트 발행은 같은 transaction에 있지 않습니다. DB commit 뒤 이벤트 발행이 실패하면
> 주문만 남을 수 있습니다. outbox로 두 작업을 묶거나 재처리 기준을 정해야 합니다.

## 장애 설명

`증상 → 직접 원인 → 근본 원인 → 영향 → 복구 → 재발 방지 → 미확인 사항` 순서를 기본으로 쓴다.
원인이 확정되지 않았으면 `원인`이라고 단정하지 말고 현재 근거와 다음 확인 방법을 적는다.

## 아키텍처 설명

컴포넌트 이름보다 책임과 경계를 먼저 설명한다. 새 추상화가 무엇을 숨기고 어떤 결합을 남기는지,
실패가 어디까지 전파되는지 적는다. 다이어그램을 쓸 때도 본문이 다이어그램의 상자를 그대로 열거하지
않게 한다.

## 자세한 설명을 요청받았을 때

원리를 충분히 풀되 문단마다 질문 하나에 답한다. 예제는 규칙을 반복하지 말고 규칙이 실제로 어떻게
적용되는지 보여 준다. 긴 답변도 결론을 맨 앞에 둔다.
