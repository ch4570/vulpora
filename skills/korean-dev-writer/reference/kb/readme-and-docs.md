# README와 개발 문서

문서 독자가 가장 먼저 하려는 일을 앞에 둔다. 시스템을 소개하기 전에 설치, 호출, 문제 해결처럼 실제
행동에 필요한 정보를 찾기 쉽게 배치한다.

## 공통 구조

- 제목 아래 한두 문장으로 역할과 범위를 설명한다.
- 사전 조건, 실행 명령, 기대 결과를 분리한다.
- 옵션이 셋 이상이면 표나 목록을 쓴다.
- 위험한 명령에는 실행 전 조건, 영향과 복구 방법을 가까이 둔다.
- 예시 값, 경로와 환경변수는 그대로 복사해도 오해가 없게 표시한다.

공공기관 보고서 같은 문장을 피한다.

나쁨:

> 본 기능은 사용자 인증 기능을 수행하기 위한 목적으로 구현되었습니다.

좋음:

> 사용자 인증을 처리하는 모듈입니다.

## 문서 종류별 초점

- **README**: 무엇인지, 빠른 시작, 주요 설정, 검증, 자주 막히는 지점
- **API 문서**: 계약, 입력·출력, 상태 코드, 멱등성, timeout, pagination, 호환성
- **아키텍처 문서**: 결정, 책임 경계, 데이터 흐름, 실패 모드, 기각한 대안
- **트러블슈팅**: 증상, 확인 명령, 판정 기준, 복구, 재발 방지
- **PR 설명**: 왜 바꾸는지, 핵심 diff, 검증 증거, 위험과 배포·rollback 조건
- **테스트 설명**: 보장할 동작, 입력 경계, 관찰 결과, 의도적으로 제외한 범위

## 문장과 목록

한 문장에 배경, 원인, 구현, 결과를 모두 넣지 않는다. 순서나 비교가 핵심이면 목록이나 표로 바꾼다.
반대로 항목이 하나뿐인데 제목과 목록을 겹겹이 만들지 않는다. 구조는 내용을 빨리 찾게 할 때만 쓴다.

문서의 기존 어미를 따른다. 기준이 없으면 내부 설계 문서는 `~한다`, 사용자용 안내는 자연스러운
`~합니다`를 쓸 수 있다. 어느 쪽이든 같은 어미가 기계적으로 이어지지 않게 문장을 연결한다.
