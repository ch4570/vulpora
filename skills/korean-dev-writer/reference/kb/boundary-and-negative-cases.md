# 경계와 잘못된 극단

## 짧게 만들면 안 되는 내용

다음 내용은 필요한 조건, 영향과 복구 방법을 충분히 남긴다.

- 보안상 중요한 제약과 신뢰 경계
- 데이터 유실·중복·불일치 가능성
- race condition, deadlock, 순서 보장
- schema·index migration 위험과 rollback
- 하위 호환성과 API 계약
- transaction 시작·commit·rollback 경계
- 배포, 삭제, alias cutover처럼 복구하기 어려운 작업
- 사용자가 원리나 trade-off를 자세히 요청한 설명

예를 들어 `alias를 전환한다`만 쓰지 않는다. 새 index 검증, 원자적 전환 여부, 이전 index 보존 기간과
rollback 조건이 작업 안전성에 필요하면 함께 적는다.

## 하지 않는 일

- 무조건 반말로 바꾸지 않는다.
- 인터넷 커뮤니티 말투나 비속어를 쓰지 않는다.
- 모든 문장을 짧게 잘라 관계를 끊지 않는다.
- 모든 전문 용어를 영어로 남기거나 모두 한글로 번역하지 않는다.
- 맞춤법만 검사하고 구조와 정보 순서를 그대로 두지 않는다.
- 자연스럽게 보이려고 사실, 불확실성, 수치와 심각도를 바꾸지 않는다.
- 설명이 부족한데 문체 규칙으로 빈칸을 상상해 채우지 않는다.

## 모호한 원문

의미가 둘 이상이면 가장 그럴듯한 뜻으로 고쳐 확정하지 않는다. 안전하게 보존할 수 있는 부분만 쓰고,
결정에 필요한 사실을 짧게 묻거나 `확인 필요`로 분리한다. 코드·로그·문서가 서로 다르면 최신 근거를
확인하기 전까지 하나를 진실로 만들지 않는다.

## 스타일 충돌

저장소의 기존 문체가 이 가이드와 다르더라도 정확하고 일관된 스타일이면 기존 문체를 따른다. 다만
공격적인 리뷰, 오해를 부르는 번역, 위험을 숨기는 축약은 기존 관례라는 이유로 유지하지 않는다.
