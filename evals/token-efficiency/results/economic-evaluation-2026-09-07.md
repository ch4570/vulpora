## 실제로 바꾼 부분과 반복 과정

1. 기존 상태를 동결한 뒤, 작은 작업의 지침을 진입 파일에 모으고 standard/audit 참조는 해당
   경로에서만 읽도록 바꿨습니다. 지원되는 설치 명령으로 `start-task`와 선언된 의존성만 설치하면
   발견되는 Vulpora 스킬이 전체 62개에서 3개로 줄어듭니다.
2. 첫 후보를 양수 문제로 세 조건 비교했습니다. 기존 143,067 → 후보 105,828토큰으로 26.0%
   줄었지만 기본 환산값은 **11.4% 증가**했습니다. 그 결과를 경제적 성공으로 처리하지 않았습니다.
3. 두 번째 후보는 이미 주입된 진입 지침을 재사용하고, 독립적인 파일 읽기를 묶도록 했습니다.
   작은 작업으로 예상되는 경우 선택기 성공과 실제 `lightweight` 결과를 확인한 뒤에만 준비된 수정·
   검증을 같은 도구 호출에서 이어갑니다. 실패·다른 경로에서는 수정 전에 중단합니다.
4. 두 번째 후보를 동결하고 위의 18회 비교를 실행했습니다. 두 후보와 이전 지침은 각각 보존했습니다.

필수 지침 문자열은 `tiktoken 0.14.0 / o200k_base`에서 기존 진입+필수 참조 **2,075 → 923토큰
(55.5% 감소)**입니다. 이 문자열 수치와 위의 실제 작업 전체 사용량은 별도 측정입니다.
위험 선택기의 의미는 바꾸지 않았고, 일곱 위험 신호의 audit 강제 전환과 잘못된 입력 거부를
오프라인 검사했습니다.

## 품질 평가에서 확인한 것과 놓친 것

고정 평가에서는 작성된 테스트, 별도 정답 검사, 기존 테스트만으로 통과하지 못하게 하는 기본 변형
검사, 허용 파일 범위를 확인했습니다. 채점기 자체도 정상·오류·누락 테스트, 경로 별칭, 중첩 Node
테스트 환경 등으로 검증했습니다. 정답 검사에는 LRU의 `undefined` 값 사용 순서, 재시도 옵션 전달,
대기 순서와 오류 객체 동일성 같은 경계 조건도 포함합니다.

별도 코드 검토에서 첫 양수 문제의 실제 구현은 세 조건이 바이트 단위로 같았습니다. 개선판의 테스트는
명시적 기대값을 썼고, 미적용의 일부 테스트는 구현식을 반복해 기대값을 계산했습니다. 다만 이 검토는
조건 이름을 아는 상태에서 수행했으며 세 문제의 일반적인 유지보수 품질 점수는 아닙니다.

LRU 첫 반복의 결과를 읽은 뒤, 추가로 선택한 세 결함을 넣고 작성된 테스트가 잡는지 확인했습니다.
이 진단은 사후에 고른 예시이며 **고정 수락 기준이나 일반적인 mutation 점수가 아닙니다.**

| 추가로 넣은 결함 | 미적용 테스트 | 기존 테스트 | 개선 테스트 |
|---|---|---|---|
| 키 갱신이 최근 사용 순서를 갱신하지 않음 | 탐지 | 탐지 | 놓침 |
| 없는 키 조회가 `undefined` 항목을 삽입함 | 놓침 | 탐지 | 놓침 |
| `has`가 저장된 `undefined`를 없다고 판단함 | 놓침 | 탐지 | 탐지 |

개선 테스트에서는 갱신 뒤의 `get`이 사용 순서를 다시 바꿔 갱신 결함을 가렸고, 없는 키 조회의
크기 검사를 조회 전에 수행해 삽입 결함을 놓쳤습니다. 코드가 현재 정답이라는 사실과 작성된 테스트가
미래 결함을 잘 잡는다는 사실을 구별해야 합니다. **테스트 품질이 항상 유지·개선됐다고 주장할 수 없습니다.**
[추가 진단의 변형 규칙·결과·해시](economic-lru-posthoc-2026-09-07.json)를 보존했습니다.

## 비용과 실험비 회수

USD는 실제 청구액이 아닙니다. 2026-09-07 공식 Terra 단가의 standard 단문맥 요청 시나리오를
적용했습니다: 백만 토큰당 일반 입력 $2, 캐시 입력 $0.20, 출력 $12. 기본값은 캐시 쓰기 추가 요금이
0인 가정이고, 범위의 상단은 모든 비캐시 입력이 캐시 쓰기인 가정입니다. Fast 시나리오는 이 금액의
두 배입니다. [모델 단가](https://developers.openai.com/api/docs/models/gpt-5.6-terra),
[서비스 등급·캐시 쓰기 단가](https://developers.openai.com/api/docs/pricing).

| 측정 범위 | 독립 작업 실행 | 실제 총 토큰 | standard 환산 범위 |
|---|---:|---:|---:|
| 최종 비교 | 18 | 1,700,659 | $1.41749–1.57224 |
| 이번 개선의 예비 비교 + 최종 비교 | 21 | 1,995,253 | $1.62948–1.81233 |
| 앞선 4회 단일 문제 비교까지 포함 | 25 | 2,329,125 | $1.85813–2.07219 |

기본 시나리오에서 기존 대비 성공 작업당 절약액은 **$0.00902473**입니다. 이 절약이 그대로
반복된다면 이번 21회 측정비 회수에 **181건**, 앞선 4회 비교까지 합치면 **206건**의 같은 구성
작업이 필요합니다. 하지만 캐시 쓰기 가정을 달리하면 기존 대비 차이는 건당 **−$0.00133135 ~
+$0.01962090**으로 절감 여부가 바뀔 수 있어 확정 회수 시점은 없습니다. 미적용 대비 절감은
이 민감도 범위 전체에서 관측되지 않았습니다.

이 계산은 해당 비교 세션들의 모델 사용량만 포함합니다. 이 대화, 개발·검토 에이전트, 이전의 별도
세션 실행기 점검, 사람의 시간과 운영비는 제외하므로 전체 개발 투자 수익이나 실제 순이익이 아닙니다.
계산기는 누락 사용량을 0으로 취급하지 않고, 절약이 불확실하면 확정 회수 건수를 `null`로 둡니다.

## 증거의 한계와 사용 판단

모든 조건은 사전에 작업 파일 해시가 같음을 확인했습니다. 캐시는 공유되며 완전히 격리하지 않았습니다.
양수 문제는 첫 후보 튜닝에 사용했으므로 이후 반복을 독립된 미사용 문제로 부르지 않습니다.
세 개의 합성 문제와 조건당 두 번의 실행으로 통계적 품질 동등성이나 일반적인 생산성 향상을 증명할 수 없습니다.

기존·개선 조건 모두 스킬 진입 본문의 주입·읽기 증거는 0/6이며, 선택기 출력은 각각 5/6에서
관측됐습니다. 자동으로 주입된 지침을 다시 읽지 않는 실행은 관측기가 로딩을 확인하지 못할 수 있습니다.
따라서 엄격한 절차 검증은 **`comparable: false`**로 유지합니다. 설치·명시적 호출 조건에서 관측한
결과이며, 두 하네스의 전체 절차를 모두 검증한 비교는 아닙니다. 요청 모델과 실제 백엔드·서비스 등급,
개별 요청의 문맥 길이·캐시 쓰기량·청구액도 별도로 입증하지 않았습니다.

이 표본에서는 작고 명확한 작업을 직접 처리하는 편이 경제적입니다. 하네스가 필요한 작업은 선택 설치와
짧은 경로로 불필요한 입력을 줄일 수 있지만, 토큰 감소만으로 자동 채택하거나 테스트 품질까지 좋아졌다고
판정하지 않습니다. 감사·보안·파괴적 작업의 절차는 이번 작은 작업 결과로 완화하지 않습니다.
추가 유료 호출은 여기서 종료하고, 다음 반복은 별도의 가설·고정 검증·예산으로 시작합니다.
